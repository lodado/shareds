# 컴포넌트 설계 가이드

디자인 시스템·공용 컴포넌트를 설계·구현·리뷰할 때의 판단 기준. 다른 개발자가 안전하게 조합할 수 있는 컴포넌트를 만드는 것이 목표다.

## 우선순위

① 컴포넌트 API 설계 → ② 인터랙션·접근성 → ③ 일관성·확장성 → ④ DX·유지보수성 → ⑤ 판단 근거 문서화

우선순위가 충돌하면 항상 낮은 순위를 희생한다. 예: 화려한 데모(④)보다 키보드 동작(②)이 먼저다.

## 1. 컴포넌트 API 설계 (최우선)

- API 시그니처만 보고 사용법을 예측할 수 있어야 한다. 문서를 읽어야만 쓸 수 있는 API는 실패다.
- boolean prop 증식 금지. variant가 늘어날 조짐이면 합성(compound component) 또는 유니언 타입으로 설계한다.
- 상태(로직)와 표현(스타일)을 분리한다. headless 구조를 쓰되, **왜 필요한지 설명 가능한 범위까지만** 적용한다.
- controlled/uncontrolled 정책을 컴포넌트 전체에서 일관되게 유지한다 (`value`/`defaultValue` + `onChange` 컨벤션).
- 잘못 쓰기 어려운 API를 만든다: 불가능한 상태 조합은 타입으로 차단, 필수 조합 누락 시 명확한 런타임 오류 메시지.
- Radix UI 같은 레퍼런스는 참고만 한다. 구조를 그대로 복제하지 말고, compound component·headless가 이 프로젝트에서 왜 필요한지 근거를 남긴다.

## 2. 인터랙션과 접근성

스크린샷이 아니라 동작이 품질이다. 컴포넌트마다 다음을 구현·검증한다.

- 키보드 조작 (Tab, Enter, Space, Arrow, ESC)
- 포커스 진입·이동·복원 (오버레이 닫힘 시 트리거로 복원)
- ESC 및 바깥 영역 클릭으로 닫기
- 역할에 맞는 ARIA 속성 (`role`, `aria-expanded`, `aria-controls` 등)
- disabled·loading 상태의 실제 동작 (클릭 차단, 중복 제출 방지)
- 이벤트 중복·전파 처리 (더블탭, 빠른 반복 입력)
- 오버레이: 스크롤 잠금 + 포털
- 터치 환경: 터치 타깃 최소 44px, 빠른 연타 방어, 실수 복구 경로, 320px~대형 화면 대응

## 3. 일관성과 확장성

- 색상·간격·타이포는 토큰으로만 사용한다. 임의 값 하드코딩 금지.
- 토큰은 의미 기반으로 명명한다 (`color-primary` ❌ → `color-action-primary`, `color-surface-raised` ⭕ 같은 역할 기반).
- variant·size 체계를 모든 컴포넌트에서 동일한 어휘로 유지한다.
- 새 브랜드·폼팩터·상태 추가 경로를 열어두되, **현재 요구사항 대비 과한 인프라(예: Style Dictionary)는 넣지 않는다.** 최소 구조 + README에 향후 확장 경로만 기술한다.
- 디자인 값(토큰)과 컴포넌트 로직의 경계를 파일 구조에서 드러낸다.

## 4. DX와 유지보수성

- TypeScript 타입과 자동완성이 문서 역할을 하도록 설계한다.
- export 구조를 명확히 한다 (배럴 export, 서브패스 export 정책 일관).
- 컴포넌트마다 사용 예시 + 상태별 Story 또는 데모를 남긴다.
- 핵심 동작(포커스, 키보드, 중복 제출 방지)은 테스트로 고정한다. 스타일 스냅샷 테스트는 지양.
- 잘못된 사용에는 개발 모드에서 명확한 오류 메시지를 낸다.

## 5. 판단 근거 (README)

README 또는 설계 문서에 다음을 짧게라도 남긴다. 결정은 내릴 때마다 기록한다.

- 요구사항 해석과 가정한 사용자
- 가장 중요하다고 본 문제
- 이 API·구조를 선택한 이유
- 고려했지만 하지 않은 것
- 시간이 더 있다면 개선할 것

"최고의 구조" 주장 금지. 제약 안에서의 선택 이유와 트레이드오프를 보여준다.
