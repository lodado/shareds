# PR 작성 가이드

PR 생성 시 `.github/pull_request_template.md` 템플릿을 반드시 사용하고, **technical-writing 스킬을 로드해서** 본문을 작성한다.

## 독자 기준

이 저장소 문맥을 전혀 모르는 초심자 리뷰어가 PR 본문만 읽고 다음에 답할 수 있어야 한다.

1. 이 PR이 무엇을 바꾸는가 (한 문장 요약을 본문 맨 위에)
2. 왜 필요한가 (배경 지식 없이 이해되는 문제 설명)
3. 어떻게 검증했는가 (재현 가능한 절차)
4. 무엇이 깨질 수 있는가

## 섹션별 작성 규칙

- **What changed**: 파일 나열이 아니라 동작 변화 중심으로. "Dialog 컴포넌트 추가" ❌ → "ESC·바깥 클릭으로 닫히고 닫힐 때 트리거로 포커스가 복원되는 Dialog 추가" ⭕
- **Why**: 요구사항·설계 결정과 연결한다. 이 PR이 전체 그림에서 어느 조각인지 한 문장으로 위치를 잡아준다.
- **How tested**: 체크박스는 실제 실행한 것만 체크. Test details에 리뷰어가 그대로 따라 할 수 있는 수동 검증 절차를 적는다 (예: "Tab으로 트리거 포커스 → Enter로 열기 → ESC → 포커스가 트리거로 복원되는지 확인").
- **Risk / Affected areas**: 영향 범위를 실제 이 저장소 패키지 기준으로 수정해서 적는다. 템플릿의 예시 패키지명을 그대로 두지 않는다.
- 전문 용어(headless, compound component, portal 등)는 처음 등장할 때 한 줄 설명 또는 링크를 붙인다.
- 스크린샷·GIF는 인터랙션 변화가 있을 때 첨부한다. 정적 스타일 변경은 before/after 스크린샷.

## 문장 편집 규칙 (technical-writing 스킬 기준)

- 한 문장에 하나의 생각. "적절히", "간단히" 같은 모호어 삭제.
- 리뷰어가 앞선 커밋·대화를 봤다고 가정하지 않는다. 필요한 문맥은 본문에 다시 적는다.
- 결론 먼저, 근거는 뒤에.
