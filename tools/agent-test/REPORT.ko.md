# Global Agent Test Scheduler 검증 보고서

측정일: 2026-11-06, macOS Apple Silicon. 구현 범위: 이 저장소의 `tools/agent-test/`. 적용 범위: 사용자 전역 CLI와 `~/orca` 대상 Claude Bash Hook. 공유 프로젝트 테스트 스크립트는 변경하지 않습니다.

> 검증 진행 중인 보고서입니다. 아래에서 미완료로 표시한 검증은 완료로 간주하지 않습니다.

## 1. 진단 결과

- 확인한 장비는 Mac17,2 / Apple M5, 물리·논리 10코어, 성능 4코어·효율 6코어, 메모리 24GiB입니다.
- 초기 CPU 표본은 약 50~75% 사용, load average 약 7.5~8.5였습니다. **당시 실행 중인 Vitest는 발견하지 못했습니다. 따라서 현재 부하의 원인을 Vitest로 단정할 수 없습니다.**
- 별도의 Next 개발 서버에서 CPU 약 122%, RSS 약 6~6.5GiB를 관찰했습니다. 스케줄러 소유가 아니므로 중단하거나 수정하지 않았습니다.
- swap 약 7.667GiB/9GiB, 압축 메모리 약 8.4~8.6GiB였습니다. 짧은 1초 간격 표본에서는 swap 증가를 관찰하지 못했고 memory_pressure의 free 표시는 약 45%였습니다. 누적 swap 사용량만으로 현재 메모리 병목을 확정하지 않습니다.
- 디스크 처리량 표본은 약 35~469MB/s로 변동했습니다. 짧은 표본으로 지속 I/O 병목은 판정하지 못했습니다.
- `pmset`에서 열·성능 경고는 관찰하지 못했습니다. 온도 및 스로틀링이 없다는 증거는 아닙니다. 권한 상승이 필요한 전력·온도 진단은 실행하지 않았습니다.
- 초기 Orca 조사에서 Git 체크아웃 33개, Vitest 선언 패키지 169개를 확인했습니다. fixtures와 worktree 중복이 포함되므로 169개 독립 서비스라는 뜻은 아닙니다. 설치된 Vitest major 2, 3, 4, 5가 공존합니다.
- 일부 프로젝트는 Vitest 선언만 있고 의존성이 없습니다. 프로젝트 의존성·브라우저 다운로드 없이 설치된 러너만 검증합니다.

## 2. 선택한 아키텍처

Python 표준 라이브러리, 사용자당 Unix Domain Socket 데몬 하나, `flock` 단일 소유권, 작업별 프로세스 그룹 가디언을 선택했습니다. 소켓 이벤트로 대기하므로 대기 요청마다 permit을 반복 조회하지 않습니다. JSON 상태는 원자 교체로 저장하며 손상된 상태는 시작을 거절합니다.

파일 잠금만으로는 FIFO, 취소와 출력 전달을 동시에 다루기 어렵습니다. SQLite는 영속 큐에 적합하지만 프로세스 수명·출력 연결은 여전히 별도 구현이 필요합니다. 이 MVP는 재실행 부수 효과를 피하기 위해 장애 후 대기 작업을 자동 재생하지 않으므로 별도 DB가 필요하지 않습니다. Rust는 배포 빌드가 추가되고, Node는 본 OS 조정 코드에 필요한 이점을 입증하지 못해 채택하지 않았습니다.

정책 A는 실행당 설정 워커 수를 예약하는 fixed 방식, B는 요청 워커 수를 예약하는 weighted 방식입니다. 둘 다 실행 수 상한과 엄격한 FIFO를 적용합니다. generic 작업은 전체 예산을 독점 예약합니다. 동적 정책 C는 측정 노이즈와 안정화 복잡도를 피하기 위해 구현하지 않았습니다.

## 4. 동시성 안전성

- 예약 토큰의 합은 예산 이하이고 실행 수는 설정 상한 이하입니다.
- 실행 예약을 먼저 저장하고 가디언 PID를 저장한 뒤에만 테스트 실행을 허가합니다.
- 가디언이 죽어도 자식 그룹이 남아 있으면 토큰을 반환하지 않고 새 실행을 차단합니다.
- heartbeat 만료나 출력 EOF만으로 토큰을 회수하지 않습니다.
- 복구 시 숫자 PID만 근거로 프로세스를 종료하지 않습니다. PID 재사용이 의심되는 경우 불필요하게 기다릴 수 있지만 무관한 프로세스를 죽이지 않습니다.
- 같은 작업 자동 재실행은 하지 않습니다. 실패한 테스트의 재시도는 호출자가 명시적으로 요청합니다.
- FIFO와 실행·대기 deadline은 정상 조건에서 무기한 추월을 막습니다. 앞의 큰 작업 때문에 빈 토큰을 활용하지 못하는 head-of-line blocking은 남습니다.

아직 최종 합동 회귀 테스트 결과는 기록 전입니다.

## 5. 장애 복구 검증

초기 가디언 SIGKILL 회귀 테스트에서 EOF 처리와 출력 drain 사이의 신규 admission 문제가 재현되었습니다. Sol core 작업에서 프로세스 종료 상태와 격리를 함께 확인하도록 수정 중이며, 최종 재실행 결과는 아래 검증 표에 기록합니다.

| 검증                         | 상태    | 범위                                                       |
| ---------------------------- | ------- | ---------------------------------------------------------- |
| 초기 어댑터·Hook·설치 테스트 | PASS    | Vitest 전용 초기 19개. 최종 다중 러너 결과를 대신하지 않음 |
| 초기 생명주기 테스트         | FAIL    | 16개 중 1개 가디언 SIGKILL admission 회귀                  |
| 최종 합동 회귀 테스트        | NOT_RUN | 구현 완료 후 조정자가 재실행                               |

| 설치된 CLI·설정 보존 검증    | NOT_RUN | 안전성 검증 후 사용자 전역 설치 예정                       |

모든 기준선 작업의 종료 코드는 0이었습니다. `ps %cpu`는 프로세스 수명 평균 계열이며 정밀 구간 사용률이 아닙니다. RSS는 프로세스 트리의 표본 합계이고 순간 최대나 공유 페이지를 제거한 실제 물리 메모리가 아닙니다. wait4 CPU는 기다린 자손을 포함하지만 detached 자손까지 보장하지 않습니다. 별도 개발 서버와 다른 에이전트의 부하는 통제하지 못했습니다.

이 기준선만 보면 2×2는 기본 무제한보다 빠르고 메모리가 적지만, 4×2보다 느립니다. 따라서 CPU 사용 감소만으로 최적이라고 평가하지 않습니다. **전역 스케줄러 자체의 전후 비교는 아직 기록 전입니다.**

## 7. M5 권장 설정

검증 출발점은 budget=4, workers=2, max_runs=2, policy=fixed입니다. 이는 처리량 최적값이라는 결론이 아니라 다른 개발 작업을 위한 여유를 두는 초기값입니다. 전후 비교 완료 후 유지 또는 변경 근거를 추가합니다. 토큰은 OS CPU 상한이 아니며 테스트의 임의 스레드와 브라우저·러너 부수 프로세스는 별도 CPU를 사용할 수 있습니다.

## 8. M5 Pro 확장 설정

15/18코어 기기에서 실측하지 않았습니다. 코어 수만으로 성능·효율 코어 구성을 추정하지 않습니다. 새 기기의 `sysctl` 토폴로지와 기존 부하를 확인한 뒤 15코어는 6토큰·2워커·3실행, 18코어는 8토큰·2워커·4실행을 **실험 후보**로 비교할 수 있습니다. 이는 성능 보장이 아니며 4토큰 기준선과 동일 작업 중앙값, P95 대기, 실패율, 메모리 압박으로 채택 여부를 결정합니다. 기본값 자동 계산과 명시 설정 변경을 모두 지원합니다.

## 9. 남은 문제와 적용 경계

- Hook은 협조적 실행 유도 장치이며 모든 임의 셸 프로그램을 가로채는 샌드박스가 아닙니다. 터미널 직접 호출, 다른 에이전트 도구, 동적 스크립트, Hook 비활성화, 별도 상태 경로는 우회할 수 있습니다.
- `~/orca` 밖 연결 워크트리는 Hook scope 목록에 추가해야 합니다. CLI는 경로와 관계없이 같은 사용자 예산을 사용합니다.
- 테스트가 setsid로 그룹을 벗어나거나 기존 외부 개발 서버에 작업을 맡기면 완전한 자원 회수를 보장하지 못합니다.
- generic은 내부 병렬성을 제어하지 않습니다. 단순 package 스크립트를 직접 러너로 풀어 실행할 때 npm lifecycle 환경은 생성하지 않습니다. 해당 의미가 필요하면 generic으로 원래 명령을 실행합니다.
- CLI 옵션과 상위 설정으로 일반 러너 워커를 제한하지만 사용자 정의 pool, browser 프로젝트와 테스트가 만드는 추가 스레드까지 OS 차원에서 제한하는 것은 아닙니다.
- Hook 실행 실패·타임아웃의 비차단 가능성, 24시간 운영, 실제 Claude 세션 10개의 end-to-end 행동은 미검증 범위입니다.
- 별도 reviewer 에이전트를 생성하지 않고 조정자가 구현을 직접 검토합니다. 구현자 자체 테스트와 조정자의 테스트를 독립 제3자 감사로 표현하지 않습니다.

## 10. 사용법과 운영 가이드

```sh
python3 tools/agent-test/install.py install
~/.local/bin/agent-test run -- pnpm test
~/.local/bin/agent-test run -- pnpm exec playwright test
~/.local/bin/agent-test run -- node --test example.test.mjs
~/.local/bin/agent-test run --runner generic -- python3 -m pytest
~/.local/bin/agent-test status --json
~/.local/bin/agent-test cancel JOB_ID
```

설정 변경은 idle 상태에서 `stop` 후 `config --set`을 사용합니다. `recover`는 사라진 그룹의 격리만 해제하며 살아 있는 과거 PID를 자동 종료하지 않습니다. 설정·상태 파일을 삭제해 활성 작업을 무시하지 마세요. 설치·업그레이드·제거와 Hook 범위, 워커 옵션, 로그 정책은 `README.md`를 참조하세요.
