# Explain the game flow before Figma writes

Use [player flow](../player-flow.md). Link stable journey, rule, screen/state and acceptance IDs. Required fields: player context, task/choice, entry, first meaningful action, success/failure, restart, pause, overlay, cancel/back, input/focus and policy boundaries.

Show five things before first target write: purpose and structure; adopt/reject source rationale; numbered text wireframes with actual UI copy; core route plus failure/recovery/focus; mapping to verified editable assets or gaps. No approval is implied by the explanation.

Use 1–3 key states; loading/error/empty/permission variants apply only when relevant. An empty playfield should invite meaningful play rather than show a generic no-data card. Guidance dismissal is not activation.

Compare similar-task observed screens separately from editable-source comparisons. A discovered screenshot is not an importable component. Any required import preflight is a write and follows the explanation/review-wait.

The game/lifecycle state model remains a design proposal. Figma prototype reactions express only scoped navigation. Read [prototype workflow](prototype-workflow.md) for actual readback.
