# Evidence-led reference research

Start with two or three different sources relevant to the player's actual decision, not a large moodboard of unrelated games. Record source URL, date/version, device/state, access depth, observed behavior, interpretation, adoption/rejection and uncertainty. Search snippets, title art and presumed popularity cannot establish game rules or business success.

Distinguish four source classes:

1. game rules/decision structure;
2. navigation, onboarding, failure and replay behavior;
3. visual composition and feedback;
4. editable or licensed production assets.

A video can demonstrate a transition but is not an editable HUD component. A UI kit can supply an editable button but cannot prove its flow is usable. An original game mechanic does not need two imported UI kits to be proposed.

Use official game pages, first-hand play or clearly scoped footage for claims. Never describe unperformed play as an observation. Third-party interpretation remains attributed. No artwork or UI copying beyond confirmed rights.

For Figma only, read [component source gate](figma/component-source-gate.md). Verify internal fit first. Missing role/content/state/device fit triggers distinct-source comparison. Preserve linkage/copy/derivative distinctions and record real imports. A gate HOLD affects the dependent UI role, not independent game planning.

This fork has no mandatory external taxonomy dictionary. Optional dictionaries remain user-local and unbundled. Unknown entries stay unknown. Search by player task + HUD/overlay role + state/device, not invented taxonomy IDs.

The log is the single source/evidence ledger. Do not create a fake bibliography with URLs that were never examined. Publicly referenced books are intellectual sources, not licensed game art.
