# Contract review and evidence limits

Use the shared review role's explicit mode and input boundary. Card-only cold-read receives card bytes
alone, asks per row: which source-approved outcome, given/action, observable then, falsifying condition
and real realization plan? Return one root and cheapest falsifying nail, not policy approval.
Reverse-impossible receives only impossible dispositions and the witness/falsifier table. Build a
counterexample and return disagreements as unresolved findings. Source-aware review separately compares
approved excerpts/actual answers with every affected decision, no blind-context contamination.

Delivery review receives matching profile/lock/source hashes, current target snapshot, raw reporter
evidence and applicable criteria. Compare actual reported case ID sets with required executable IDs,
not declared labels, aggregate counts, planned tests or a handwritten manifest. Check duplicate/stale/
missing IDs, excluded/held cases and mapping to approved expected outcomes. Verify applicable type-fest/
TypeScript consumer diagnostics on final bytes. Verify the recorded applicability determination before
accepting omission of `type-contract:reported`: exact investigated file paths, grounded no-boundary rationale
and its approved source, not self-approval or semantic-runtime inference. Intake/authoring owns investigation.
Unknown applicability requires further investigation; unavailable required tools are an actual environment
failure, not N/A.
When Async/Order is active, verify `fast-check:reported` against approved contract invariants,
independent of an exposed type boundary and without Bend comparison. Check a positive actual execution count,
seed, domain, sampling scope, current snapshot and shrink evidence on failure on final bytes.
Required missing evidence or producer capability is failure, not inferred success.

For `contract-cases:reported`, inspect actual unique terminal names retaining `[<frame ID>]` and
exactly one `oracle-case:<base64url JSON>` token. Compare decoded `id`, `scenario`, `tuple`,
`dimensionRevision` and `constraintRevision` with the current locked full-product records and exact
frame-map/row/sequence names. Check all required observed IDs and passed terminals, not metadata
assertions. Labels/identity do not prove source completeness or meaningful product assertions.

For `type-contract:reported` and `fast-check:reported`, check the two fixed Node diagnostic REQUEST
shapes and actual producer output, not ordinary labeled passing tests. Vitest supplies actual case
reporting only, not the claimed compiler/property producer capability. Check registered frozen
positive/negative/module harness paths and actual current source/manifest binding, not merely two
mutually consistent saved snapshots. Positive compiler success, distinct negative rejection with
real TS diagnostics, fixed strict/noEmit ES2022 NodeNext settings and meaningful type-fest consumer
relations must address the same approved sources. Import matching alone is syntactic evidence.

Check that the companion exports a real fast-check property, nonempty string `domain`, safe-integer
`seed` and positive safe-integer requested `numRuns`, and that actual `fc.check` output supplies positive
execution count, actual seed and failure/shrink/counterexample/path information. Domain is declared
companion metadata, not an independently measured domain. Requested counts are not measured counts.
Check approved invariant/domain relevance and sampling limits separately. Producer failure cannot pass
solely because the native wrapper exits zero. Missing dependency, path/setup/timeout infrastructure
must not furnish genuine RED in a mixed nonzero run or be replaced by ordinary tests.
Actual compiler rejection/property falsification remains distinct.

Requests are currently globally name-keyed rather than bound to the emitting file/test scope.
Registered-input hashes and genuine execution do not establish per-test request attribution,
cryptographic authentication, independent proof or assertion relevance. Malformed/unmatched requests
may be ignored, so do not claim universal explicit schema rejection.

Compare the actual status verification summary with the existing `status --check-report <file>`
fields: unique exact `Profile`, `Coverage`, `Executed unique`, `Passed unique`, `Formal verification`,
plus existing state/run/exit checks. Contract values are `contract/v1`, `full-product` and
`not-performed`. Before execution unique counts are `null` and `executionStatus` is `not-run`.
Stale/incomplete evidence must not gain verified counts. Separate declared Space/audit, actual unique
execution/pass counts and residual uncertainty. Use the [selected-profile loader](../roles/loading.md)
for named current-stage criteria. Controller-only approval/receipt ownership remains unchanged.

Return findings only with exact cases/rows/evidence, checked scope and residual uncertainty. Never issue
receipts, transitions, policy approval or edit product/tests/lock. Preserve High hardening and independence.
Report `formalVerification: not-performed`, finite full-product coverage, source completeness limits and
sampling/type/observation limits separately. Mechanical completion is not unbounded correctness proof.
