## Architecture plan (proposal; boundaries only, no file layout yet)

1. **Tenant-scoped query key.** The key is `[tenantId, resource, normalizedParams]`. `tenantId` is mandatory and
   first. A key cannot be built without it. Tenant identity is never read from ambient state at fetch time; it is
   captured when the query is created.
2. **Cache store partitioned per tenant.** One `Map<tenantId, Map<keyHash, Entry>>`, not a flat map. Entry =
   `{ data, status, fetchedAt, requestId }`. Dropping a tenant partition is O(1) and cannot touch another tenant.
3. **Request lifecycle.** The state machine per (tenant, key) is `idle → pending → ok | fail | unknown`.
   Every fetch carries a monotonically increasing `requestId` and an `AbortSignal`. A response commits only if its
   `requestId` is still the latest for that key AND its `tenantId` equals the active tenant. Otherwise it is dropped,
   with no screen or cache write.
4. **In-flight dedup.** Concurrent subscribers to the same (tenant, key) share one request (request count = 1).
5. **Placeholder data.** A placeholder is rendered with an explicit `isPlaceholder` flag. It is never written to
   the cache as real data and never counts as `ok`. Allowed sources are same-tenant only (see Q3). A placeholder must
   not be derived from another tenant's entry.
6. **Tenant switch.** On switch, the view re-binds to the new tenant's partition. The previous tenant's in-flight
   requests are aborted and their late responses discarded. The previous tenant's data is never visible, even for one frame.
7. **Staleness and invalidation.** Staleness is time-based, with time modeled as a `Tick`/`Expire` event, not a clock
   read. Mutations invalidate by exact (tenant, resource) prefix only.
8. **Session/permission boundary.** A 401/403 or tenant-membership loss purges that tenant's partition (see Q5).
9. **Layers.** Pure core (key, reducer/state machine, commit guard) is separated from the adapters (fetch, timers,
   rendering). Only the pure core is modeled formally; I/O and rendering are listed as Not formalized.

Not formalized (Oracle will not verify): visual layout of the placeholder/skeleton, animation timing, real network behavior.

Interaction sweep:
- pending × late-after-switch → covered(R7)
- ok × inverted → covered(R8)
- fresh × mount → covered(R3); stale × mount → covered(R4)
- fail × placeholder → needs-decision: Q3, Q6
- unknown × tenant switch → needs-decision: Q4
- idle × late response → impossible: no request in flight to deliver one
- stale × tenant switch → covered(R6); stale data of the previous tenant is never shown
- ok × membership lost → covered(R12)

## Open questions

- Q1 In-flight dedup: (a) ★ share one request per (tenant, key); (b) one request per subscriber.
- Q2 Freshness: (a) ★ stale-while-revalidate with a fresh window (duration to be set, default 30s); (b) always refetch on mount; (c) no refetch until invalidated.
- Q3 Placeholder source: (a) ★ static or same-tenant data only, flagged `isPlaceholder`; (b) previous-key data of the same tenant kept while the new key loads; (c) no placeholders.
- Q4 Tenant switch: (a) ★ abort the old tenant's requests and keep its cache partition; (b) abort and purge it; (c) let it finish in the background.
- Q5 Access loss (401/403 or membership removed): (a) ★ purge that tenant's partition immediately; (b) keep it until the next switch; (c) keep it until reload.
- Q6 Failure display: (a) ★ show the error and keep the last good same-tenant data, marked stale; (b) show the error only; plus: retry on definitive failure is manual; on unknown outcome, retry is allowed for reads.
- Q7 Mutation invalidation: (a) ★ exact (tenant, resource) prefix; (b) the whole tenant partition; (c) none, TTL only.
- Q8 Cache lifetime / memory: (a) ★ per-tenant LRU cap (size to be set) with eviction on unmount-after-grace; (b) unbounded for the session.

Reply `yes` to adopt every ★ and confirm axes + Draft, or `Q<n>=<option>` to swap one.
Numbers marked "to be set" (fresh window, LRU cap) are unspecified in S1 and stay open until answered.
