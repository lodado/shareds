## Architecture plan

1. **Tenant scope is part of every cache key.** Key factory `tenantKey(tenantId, resource, params)`
   → `["t", tenantId, resource, params]`. Callers cannot build keys without a tenantId (type-level: branded
   `TenantId`). A view mounted with no active tenant renders nothing and fires no request.
2. **Cache store (per-tenant partitions).** `Map<TenantId, Map<QueryHash, Entry>>`. Entry =
   `{ data, fetchedAt, status, error?, inflight? }`. Reads and writes always go through the partition for the
   tenantId captured when the request was *issued*, never the "current" tenant at response time.
3. **Request lifecycle.** `observe(key)` → state machine
   `idle → pending → ok | fail`, with `ok → stale` by clock event `Expire`. A single in-flight promise per
   key is shared by all observers (dedup). Each fetch carries an `AbortController` and the issuing
   `(tenantId, requestSeq)`.
4. **Late-response guard.** On resolution: write into the *issuing* tenant's partition only; the view
   re-renders from the *active* tenant's partition. A response for a non-active tenant is stored (or dropped,
   Q4) but can never reach the rendered output.
5. **Placeholder data.** Placeholder is a view-layer value, never written to the cache as real data.
   Rendered state carries `isPlaceholder: true`; consumers/UI must distinguish it (visual + `aria-busy`,
   no actions that need real data). Placeholder source is per-tenant or generic (Q3); it must never be
   another tenant's real data.
6. **View states** (exactly one rendered): `no-tenant`, `loading` (miss, no placeholder), `placeholder`
   (miss + placeholder, fetch pending), `data` (fresh), `data+refreshing` (stale, background fetch),
   `data+error` (cached data, refetch failed), `error` (no data), `empty` (ok, 0 items).
7. **Invalidation & lifetime.** Tenant switch does not evict by itself (Q1). Logout / permission loss purges
   (Q7). `gcTime` evicts unobserved entries (Q8). Mutation-driven invalidation is out of scope until a write
   path exists (Q9).
8. **Boundaries.** `TenantProvider` (active tenant, switch), `QueryCache` (partitions, dedup, gc),
   `useTenantQuery` (observer → view state), `TenantDataView` (render + a11y: `role="status"`/`aria-live`
   for loading/error, accessible name, keyboard retry).
9. **Verification (planned, not run).** Deferred-response barrier per fetch; assert visible data AND request
   count; both release orders for the A/B switch race; per-test isolated cache and fake clock for `Expire`;
   Bend model of {tenant, cache, fetch, order} with a "tenant leak" property: rendered data ∈ active
   tenant's partition ∪ placeholder. Consumer tests require explicit Delivery request.

## Open questions
- Q1 Tenant switch and cache: (a) ★ keep each tenant's partition, show only active (b) clear previous tenant's cache on switch
- Q2 Freshness: (a) ★ per-resource `staleTime`, default 30s, stale = show + background refetch (b) always refetch on mount (c) never stale
- Q3 Placeholder source: (a) ★ static per-resource skeleton shape, never real data (b) last-known data of the *same* tenant+key (c) none
- Q4 Late response for non-active tenant: (a) ★ write to its own partition, never render (b) discard
- Q5 Error handling: (a) ★ keep cached data + error banner; no auto-retry, manual retry (b) auto-retry with backoff (c) drop cache on error
- Q6 Dedup scope: (a) ★ one in-flight request per tenant+key (b) no dedup
- Q7 Persistence/security: (a) ★ memory-only cache; purge tenant on 401/403; purge all on logout; reload starts empty (b) persist to storage per tenant
- Q8 Eviction: (a) ★ `gcTime` 5 min after last observer (b) never evict
- Q9 Scope: (a) ★ read-only queries only; mutations/invalidation out of scope for this plan (b) include mutation invalidation
