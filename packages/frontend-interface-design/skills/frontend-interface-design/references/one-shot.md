# One-shot — 합의 뒤 한 번에 완성한다

## 정적 우선과 경험 완성

[experience-design.md](experience-design.md)를 Discovery에서 읽고 납품까지 이어 쓴다. UI·UX·모션은 함께 설계·검토한다. 정적 우선은 정적 종료가 아니며 요청된 핵심 경험이 빠지면 미완성이다. 일반 조작 피드백의 짧은 duration을 영상·브랜드·스크롤 시간축의 상한으로 확대하지 않는다.

원샷은 질문 0회나 모델 호출 1회가 아니다. **필수 정보와 시각 방향을 확정한 뒤**, 섹션별 선택을
사용자에게 떠넘기지 않고 전체 구성 · 구현 · 렌더 · 보정까지 이어서 끝낸다. 사실 확인과 디자인
판단을 구분하며, 필요한 답변을 받지 못한 상태를 "완료"로 바꾸지 않는다. 준비에서 브랜드·출력·
위임을 합의하고 실행에서 적용한다. 현재 범위에 유효한 승인과 실행 요청이 있으면 별도로 다시 묻지 않는다.

출력 형식·위치·편집 가능 범위와 도구 읽기/쓰기 접근은 [discovery.md](discovery.md), 브랜드
원본·토큰·충돌·누락 처리는 [brand-intake.md](brand-intake.md)를 따른다. 코드 구현은 합의된
출력일 때만 수행한다. 편집본을 이미지 한 장으로 대신하거나 미확인 도구 기능을 가정하지 않는다.

## 1. 우선순위 — 위가 아래를 이긴다

```
1. 안전 · 권한 · 법                 결제 · 삭제 · 권한 정책은 frontend-oracle-design 소관.
                                    없으면 NEEDS_DECISION. 무단 자산 · 코드 복제 금지.
2. 접근성 하한                       대비 4.5:1 / 3:1, 탭 타깃, focus-visible, 320px overflow 0.
                                    레퍼런스가 이걸 어기면 레퍼런스를 고친다(이탈로 기록).
3. 사용자 소유 소스 · 잠긴 DESIGN.md 보존 범위와 확정된 브리프를 따른다.
                                    새 방향은 사용자 선택/명시적 위임 범위에서만 정한다.
4. Reference Pack의 observed 값      선택한 방향의 관측 기반 기본값. 계보보다 우선한다.
5. Reference Pack의 estimated 값     관측값에서 유도한 기본값. 근거와 미확인 부분을 적는다.
6. 계보(lineage)의 기본값            관측 자료가 부족한 부분의 출발점.
7. craft 기본값 · 미적 선호          위 기준과 충돌하지 않을 때 적용되는 마감 기본값.
```

**5–7단은 법이 아니라 기본값이다.** accent 5% · 폰트 2개 등의 미적 기본값은 관측 자료와 선택한
방향에 맞춰 조정할 수 있다. 관측된 팩이 다른 값을 말하면 계보보다 팩이 이긴다. 예: Vercel 팩의
primary CTA는 무채색 반전이다. 차이는 decision record에 적고 접근성 하한은 유지한다.

기존 디자인의 보존 범위를 바꾸는 무드보드를 조용히 잠그지 않는다. 명시적 재디자인 요청이 있어도
승인된 범위만 바꾸며 기존 필수 승인 절차는 유지한다. 새 디자인은 합의된 방향을 하나의
디자인 시스템과 공통 토큰/변수로 정리한다(코드 작업은 `DESIGN.md`). 여러 출처의 전역 스타일을 그대로 겹쳐 넣지 않는다.

사용 권한이 있는 자산과 라이선스가 허용하는 코드는 출처 · 고정 버전 · 의무를 기록하고 재사용한다.
제품 사실 · 필수 콘텐츠 · 정책을 추정하지 않는다. 질문/위임의 판정은 [discovery.md](discovery.md)를 따른다.

## 2. 선택자 — 확정된 task로 팩 · scope를 정한다

```bash
node <skill>/scripts/pack.mjs --route "<사용자 발화>" --task <우리 task>
```

`mode` · `packId` · `evidenceStatus` · `taskMatch`는 라우팅 증거이지 사용자 의도의 자동 확정이 아니다.

| mode                            | 시각 기본값        | 첫 문장에 반드시       | layout slots                                                  |
| ------------------------------- | ------------------ | ---------------------- | ------------------------------------------------------------- |
| `reference-informed-adaptation` | 팩                 | 관측 날짜 · URL        | scope=full은 전체 후보; relationship-study는 관계별 응용 조사 |
| `unverified-reference`          | 합의된 방향 · 계보 | "브랜드 재현 아님"     | 미관측 패턴은 참고만                                          |
| `lineage`                       | 합의된 방향 · 계보 | 팩 없음·소스 확인 범위 | 제공 소스 관측 또는 역할별 후보 선택                          |

**task가 다르면 자동 이식 대신 관계별 응용을 검토한다.** `relationship-study`는 관측된 구간의
비중·정렬·정보 관계·동작을 [reference-study.md](reference-study.md)로 확인하고 실콘텐츠에서
시험하는 경로다. hero·display 크기·섹션 순서·제품 정책을 통째로 옮기거나 브랜드 재현을 주장하지 않는다.
팩의 `taskTransfer`는 자동 전용 가능한 값과 그대로 이식하지 않을 값을 구분한다. 관계의 재해석은
별도 관측·대표 구간 비교로 근거를 얻는다. task 미확정 또는 기기/테마 관측 누락의 `tokens-only`는
자동 적용의 증거 한계로 유지한다. 부족한 근거를 일반 스타일로 덮고 응용 완료라고 하지 않는다.
팩 없음은 레퍼런스 없음과 다르다. 제공 URL·스크린샷이 있으면 관측해 위 응용 경로로 연결한다.

페이지와 기기 범위는 기존 자료/사용자 답변에서 확인한다. 불명확해 구성이나 동작이 달라지면
질문한다. `pages[0]`을 사용자 요청 페이지로 간주하지 않는다. 별도 범위가 없다면 375 · 1280은
**렌더 검토 뷰포트**로 쓸 수 있지만, 이것이 제품의 지원 기기를 확인한 것은 아니다.

## 3. 질문과 위임 — 사실은 확인하고 디자인은 결정한다

[discovery.md](discovery.md)의 질문으로 중요한 빈칸을 채우고 답변을 브리프에 반영한다.
모르는 기능 · 데이터 · 가격 · 후기 · 성과를 만들어내지 않는다. 명시적으로 허용한 시안용
placeholder는 그 사실을 표시하고 실제 콘텐츠 완료와 구분한다. 위임된 시각 선택은 근거를 적고
직접 결정한다. 질문 예산이나 사용자의 침묵은 답변 · 승인 · 위임이 아니다.

방향이 미확정이면 [art-direction.md](art-direction.md)로 실제 콘텐츠 무드보드를 보여주고 하나를
추천한다. 상위 방향 선택 뒤에는 섹션마다 다시 승인을 묻지 않는다. 충분히 정해진 Fidelity는
중복 질문/새 무드보드 없이 바로 구현한다. 중요한 미확정 사실은 `NEEDS_INPUT`, 정책 · 권한
결정은 `NEEDS_DECISION`으로 남기며, 해결하지 못한 내용을 가정으로 바꾸지 않는다.

## 4. 잠금과 다양성 — 하나의 스타일, 여러 출처의 구성

- 잠긴 DESIGN.md · 선택된 방향이 있으면 스타일을 유지한다. 같은 역할은 구성을 반복해도 된다.
- 섹션 레이아웃까지 단일 계보 · 팩에 종속시키지 않는다. [section-composition.md](section-composition.md)로
  여러 출처를 비교하고 역할에 맞는 구성을 선택한다. 출처 수나 다양성 자체는 목표가 아니다.
- 잠금 전에도 마지막 화면과 다르게 만들기 위해 부적합한 구성을 고르지 않는다. 같은 구조의
  반복이 콘텐츠에 맞는지 살피고, 이유 없이 복제한 경우에만 대안을 찾는다.
- `.design/log.json`의 `locked: true`는 사용자 선택 또는 명시적 위임으로 확정된 디자인의 기록이다.
  파일 존재나 로컬 기록만으로 디자인 변경 권한을 얻지 않는다.

## 5. 상태(state)는 컴포넌트마다 다르다

상시 규칙 7의 8종은 **인터랙티브 컴포넌트의 최대 집합**이지 모든 요소의 의무가 아니다.

| 컴포넌트                    | 필수 상태                                                              |
| --------------------------- | ---------------------------------------------------------------------- |
| 제출 · 액션 버튼            | default · hover · focus-visible · active · disabled · loading          |
| 링크 · 탭 · 토글            | default · hover · focus-visible · active · current(선택)               |
| 입력 · 선택                 | default · hover · focus-visible · disabled · error · (해당 시 success) |
| 목록 · 표 · 피드            | default · loading · empty · error (행 hover는 선택)                    |
| 정적 텍스트 · 이미지 · 배지 | 없음                                                                   |

"버튼에 success 상태가 없다"는 결함이 아니다. "폼 제출 버튼에 loading이 없다"는 결함이다.

역할별 확장 상태는 `ux-taxonomy.md → 25. 상태 유형`(경로 · 읽는 법은 `dictionary-recipes.md` §0)에서 그 화면의 계약에
있는 것만 고른다: offline · stale data · partial load · conflict · rate limited · permission denied · expired. 계약에 없는
상태를 화면에 발명하지 않는다. AI 기능이 있으면 `27. AI UX 패턴`의 streaming response · AI loading/thinking ·
regenerate/retry · source citation · human-in-the-loop · AI guardrail을 해당 컴포넌트의 필수 상태 행에 넣는다.

## 6. 색 · 폰트 수 — 개수가 아니라 가족과 역할

- 색: **중립 계열 1개 + 액션 accent 1개 + 상태색(성공 · 경고 · 위험)**이 기본이다. 중립 계열이
  6단계여도 한 가족이면 하나로 센다. 세는 것은 hue 가족이지 토큰 개수가 아니다.
  팩이 추가 hue를 관측했다면(예: 가격용 경고 hue) 그것은 역할이 있는 색이므로 허용된다.
- 폰트: **가족 ≤2**는 본문 · display 가족을 뜻한다. 같은 가족의 굵기 · 폭 변형은 하나로 센다.
  모노스페이스는 코드 · 숫자 역할이면 세 번째로 허용한다(팩이 관측했다면 근거가 있는 것이다).
- `gates.json`의 `fontFamilyCount`는 렌더된 **가족 이름의 개수**를 세므로, 모노를 쓰는 브리프는
  브리프의 `gates`에서 3으로 올린다. 게이트를 임의로 완화하는 것이 아니라 브리프에 선언한다.

## 7. 한 번의 요청 안에서 도는 루프

유효한 방향 승인과 실행 요청이 있으면 "진행하겠습니다"라는 계획 선언만으로 턴을 끝내지 않고
다음 안전한 탐색·적용·렌더 행동을 수행한다. 실제 차단 사항이 있을 때만 그 이유를 보고한다.

방향 합의 뒤 Build와 [`look.md`](look.md)의 **1회 렌더 + 최대 2회 보수**를 이어서 수행한다.
필수 사실이 새로 부족해진 경우만 질문 단계로 돌아간다. 보정 예산이 끝나도 게이트를 완화하지 않는다.
미통과 · 미확인 항목은 Rationale의 "남은 결함"에 적고 완료 조건 미충족을 알린다.
기술 게이트 통과와 디자인 납품 가능 판정은 다르다. 핵심 콘텐츠·구성 결함이 남으면
`look.md`의 디자인 미완성 판정을 유지하며 모션·장식 보정으로 덮지 않는다.
