# Look — 실제 화면과 동작을 보고 고친다

Build 직후 **반드시** 돈다. 보지 않은 화면은 완료가 아니다. 자체 비평이며 `VERIFIED`를 발급하지 않고 독립 QA를 대신하지 않는다.
첫 렌더 1회 + 보수 최대 2회. 검사 수·집계·렌더 횟수는 미감이나 납품 가능의 증거가 아니다.

## 0. 합의된 결과를 연다

디자인/프로토타입은 실제 편집 환경의 프레임·상태·크기·편집 가능 범위를 연다. 코드 하네스나 이미지로 몰래 대체하지 않는다.
코드는 실제 앱을 우선하고, 실행 환경이 없을 때만 실제 콘텐츠·토큰의 정적 하네스를 쓴다.
`validated: actual-app`은 실제 라우트, `validated: surrogate`는 하네스만 검사했다는 뜻이다. surrogate 통과는 앱 통과가 아니다.

## 1. 렌더와 기술 검사

```bash
node <skill>/scripts/render.mjs --in <실제 URL 또는 HTML> --out design-loop/r1 \
  --viewports 375,1280 --themes light,dark --lang ko --source <실제 소스>
```

`evals/gates.json`으로 대비·overflow·작은 텍스트/탭 타깃·긴 본문·한글 줄바꿈·토큰 리터럴 비율(≤0.1)을 확인한다.
폰트 가족 수는 진단값이며 공통 탈락 기준이 아니다. 명시된 브랜드/호스트 폰트 계약은 별도로 지킨다.
Playwright가 없으면 기존 브라우저 도구로 같은 뷰포트를 관측하고 누락 metrics는 미측정으로 남긴다.
디자인에는 DOM/소스 게이트를 적용했다고 쓰지 않는다. 필요한 검사를 못했으면 해당 범위는 미검증이다.
전체 페이지 캡처의 fixed/sticky 위치는 캡처 아티팩트일 수 있으므로 실제 뷰포트에서 재확인한다.

## 2. 한 번의 비교로 검토한다

전체 축소에서 구도·강약을, 읽기 크기에서 섹션별 제목·본문·메타정보·조작을 본다. 작은 화면도 직접 연다.
기존 원본/승인 방향/대표 구간과 대응 결과를 나란히 비교한다. 브리프의 핵심 과업·필수 내용·시그니처 관계가 남았는지 본다.
이미 있는 brief 체크리스트를 재사용한다. 고정 eval은 기존 10문항을 쓰고, 별도 Craft 10문항·7축 표를 다시 작성하지 않는다.
문제가 보인 부분만 `어느 관계 → 원인 → 바꿀 것 → 전후 근거`로 기존 critique에 적는다. 점수나 yes 개수로 채택하지 않는다.

- 글 발견/작업 완료를 돕는 주인공·읽기 순서가 실제 길이 콘텐츠에서 유지되는가?
- 섹션별 역할은 다른데 타입·정렬·색 역할은 한 시스템으로 읽히는가?
- 선택한 시그니처가 가독성·상태 구분과 경쟁하지 않는가?

구성이 무너지면 색·그림자를 추가하는 대신 해당 섹션의 정보 관계를 다시 고른다. 적합한 여백·중앙 정렬 자체는 결함이 아니다.
원인 어휘가 필요할 때만 `form-quality.md` 또는 `dictionary-recipes.md`의 `ai-slop-taxonomy.md`를 쓴다.
예: `slop: Everywhere Glow → Escape: Figure-Ground`. 이름은 수정의 단서이지 새 체크리스트가 아니며 Severity를 합산하지 않는다.

## 3. 필요한 조작과 모션을 별도로 실행한다

[experience-design.md](experience-design.md)의 합의된 전이 행을 이어 쓴다: 대상·조작 → 예상 결과 → 실제 관측 → 완료/뒤로·실패/복구.
단순 필터는 결과·선택 표시·키보드를 확인하면 된다. 지원하지 않는 비동기 상태나 전체 상태공간을 만들어 검사하지 않는다.
시각 변화는 전후 캡처, 타이밍·스크롤·이동은 짧은 녹화/시간축 프레임 또는 실행한 브라우저 스크립트와 관측 기록으로 확인한다.
다운로드·클립보드·보조기술 알림처럼 픽셀로 판단할 수 없는 결과는 적합한 실행 증거/behavior test를 쓴다.
필요한 모션은 일반/축소 설정에서 같은 작업·종료·복귀를 각각 실행한다. reduced-motion 정지 캡처는 일반 모션 근거가 아니다.
확인하지 않은 행은 `unobserved`다. 요청된 핵심 경험이 빠지면 기술 게이트가 통과해도 미완성이다.

## 4. 수정의 채택과 정지

1. **하드 게이트**: 적용 가능한 `gates.json`의 모든 항목이 통과해야 한다. 미측정은 통과가 아니며 조용히 게이트를 낮추지 않는다.
2. **치명적 무퇴행**: 핵심 과업·필수 내용·접근성·주인공/위계·시그니처 관계·필수 경험을 악화시키지 않는다. 총점에 숨은 치명적 회귀는 개선이 아니다.
3. **진전**: 겨눈 결함의 개선·손실을 원본/승인 방향과 수정 전후의 비교 근거로 설명한다. 근거 부족은 `unreviewed`, 핵심 미달은 `incomplete`다.

영향 구간만 수정→재렌더→비교한다. 첫 렌더 1회 + 보수 최대 2회이며 2라운드 연속 채택되지 않으면 정지한다.
구조 재선택·선택적 polish도 같은 예산이다. 소진 시 남은 결함과 복구 지점을 알리고 완료로 바꾸지 않는다.
큰 경험 해석 오류는 실패한 시도와 영향받은 결정을 기록하고 그 적용을 멈춘다. 기존 승인 안의 복구는 직접 하고 새 사실·권한 결정만 질문한다.

## 5. 기록은 한 번

- technical: pass / fail / unmeasured / N/A — 실제 검사 대상·결과. 코드는 `loop:`와 screenshots·metrics·기존 critique를 연결한다.
- design-self-review: ready / incomplete / unreviewed — 실콘텐츠·방향 비교와 남은 핵심 결함.
- user-acceptance: accepted / rejected / not-obtained — 실제 사용자 응답만. 자기검토는 선호·사용성·성과 검증이 아니다.

새 보고 표를 복제하지 않는다. 확인한 화면을 먼저 전달하고 선택 이유·검증·잔여 범위만 설명한다. 후속 피드백은 [review.md](review.md)를 쓴다.

## 선택 도구

이미 사용 가능한 Impeccable의 browser 엔진만 보조 측정에 쓴다. 소스 스캔은 undercount이며 DOM 관측을 대신하지 못한다.
`impeccable critique`는 두 번째 의견이다. `polish`는 기존 보수 예산 안의 finisher 1회이고 이후에도 위 채택 조건으로 비교한다.
도구 설치나 `impeccable init`을 필수 절차로 만들지 않는다. 기존 `DESIGN.md` 교체 권한은 도구 결과에서 생기지 않는다(`NEEDS_DECISION`).
