# Look — 비교 근거로 채택하는 시각 루프

## 정적 렌더가 검사하지 못하는 경험

[experience-design.md](experience-design.md) §4의 여정·일반 모션·축소 모션 검토를 별도로 수행한다. 정적 render.mjs 결과만으로 시간적 경험이 검증됐다고 하지 않는다. 요구된 핵심 특징 누락은 기술 게이트 통과와 무관하게 미완성이다. 계측 오탐과 큰 방향 실패도 해당 절의 분류를 따른다.

Build 직후 **반드시** 돈다. 보지 않은 화면은 완료가 아니다. 이 루프는 자기비평이지 검증이
아니다 — `frontend-visual-qa`의 `VERIFIED`를 발급하지 않고 Oracle artifact도 만들지 않는다.

검사 수·렌더 횟수는 미감의 증거가 아니다. 기술 검사는 별도로 유지하고, 시각적 채택은 실제
비교에서 보이는 개선·손실로 판단한다. 보정 횟수는 비용의 상한이지 완료 조건이 아니다.

## 0. 준비 — 렌더 대상

먼저 합의된 출력에 따라 경로를 고른다. **디자인/프로토타입**은 실제 편집 환경의 적용 위치를
열고 화면·상태·크기·편집 가능 범위를 확인한다. 목적·콘텐츠·브랜드 자산/토큰·섹션 적합성·전체
조화·세부 완성을 점검하며 전체 축소/부분 확대/작은 화면의 증거를 남긴다. 코드나 정적 하네스를
대체 결과로 만들지 않는다. 아래 DOM/리터럴·실행 게이트는 코드용이며 디자인에는 해당하지 않는
항목과 측정 한계를 명시한다. 필수 디자인 확인이 불가능하면 완료가 아니다.

디자인 수정도 `어느 부분 → 기준 위반 → 수정 → 이전보다 개선됐는가`로 기록하고 최초 확인 뒤
보수 최대 2회로 시작한다. 합의된 필수 내용/브랜드/출력 조건을 어기거나 악화된 변경은 반려한다.
코드 산출물은 아래 하네스와 기존 하드 게이트·무퇴행·진전 규칙을 그대로 따른다.

- dev server가 있으면 그 URL. 없으면 **정적 하네스**를 만든다: `design-loop/harness.html`에
  토큰 블록(`:root` / `.dark`)과 대상 컴포넌트 · 화면을 인라인한다. 외부 요청은 폰트 CDN만.
- 하네스는 실제 카피와 실제 길이의 데이터를 쓴다. `Lorem ipsum`과 한 줄짜리 가짜 데이터는
  줄바꿈 · 밀도 결함을 숨긴다.

## 1. 렌더 + 결정론 검사 (도구)

```bash
node <skill>/scripts/render.mjs --in design-loop/harness.html --out design-loop/r1 \
  --viewports 375,1280 --themes light,dark --lang ko --source src/
```

`<out>/375-light.png` 등 스크린샷과 `<out>/metrics.json`이 나온다. metrics의 게이트는
`evals/gates.json` 기본값을 따른다: 대비 실패 0 · 가로 overflow 0 · 폰트 가족 ≤2 · 이모지
글리프 0 · 12px 미만 텍스트 0 · 24px 미만 탭 타깃 0 · 80ch 초과 본문 0 · 토큰 외 리터럴 비율
≤0.1 · (ko) keep-all 커버리지 ≥0.95.

- 게이트 실패는 채택 전에 고친다. 별도 시각 비평에는 브리프·콘텐츠·비교 화면을 먼저 제공하고
  구현자의 성공 설명과 테스트 개수로 판단을 유도하지 않는다.
- `impeccable`이 설치돼 있으면 `--impeccable`을 붙인다(browser 엔진). 소스 스캔(`detect src/`)
  결과는 undercount라서 게이트 근거로 쓰지 않는다.
- Playwright가 없으면 프로젝트의 Playwright 또는 browser MCP로 같은 뷰포트를 찍고,
  metrics는 "미측정"으로 기록한다. 스크린샷 없이 다음 단계로 가지 않는다.
- 전체 페이지 캡처에서 `fixed` · `sticky` 하단 바(탭 바 · 토스트 · 하단 CTA)는 첫 뷰포트의
  바닥, 즉 페이지 중간에 찍힌다. 캡처 아티팩트지 결함이 아니다 — 겹침으로 세지 않고, 확인이
  필요하면 뷰포트 높이를 문서 높이로 늘려 한 번 더 찍는다.

## 2. 섹션별 비평 (기존 질문과 비교 근거)

스크린샷을 **섹션 순서**로 본다: 첫 화면(hero · nav · 첫 카드 열) → 본문 → 폼 · 표 → footer.
전체를 한 번에 보면 첫 인상이 나머지를 덮는다(DCGen: 분할 비평 +15%).

두 체크리스트는 진단 질문이다. yes/no와 관찰 근거를 연결하고 보지 못했으면 `unreviewed`로
남긴다. 절대점수나 합계로 시각적 채택을 결정하지 않는다. 시간적 경험은 정적 캡처로 승인하지 않는다.

**A. 브리프 체크리스트 10문항** — Frame 단계에서 만든 것(`references/adaptation.md` § 브리프).
없으면 `evals/briefs.json`의 같은 유형 브리프 문항을 빌린다.

**B. Craft 체크리스트 10문항** (`references/craft.md` 번호 참조)

| #   | 질문                                                                                      | craft |
| --- | ----------------------------------------------------------------------------------------- | ----- |
| 1   | 2초 안에 첫 시선이 primary action 또는 primary 정보에 가는가                              | —     |
| 2   | primary / secondary / tertiary 세 층이 크기 · 무게 · 색 중 둘 이상으로 갈리는가           | —     |
| 3   | 섹션 > 그룹 > 요소 순으로 간격이 줄어드는가 (같은 gap 반복이 아닌가)                      | 9     |
| 4   | 텍스트 · 아이콘 · 컨트롤이 하나의 grid/baseline에 정렬돼 있는가 (광학 보정 포함)          | 12    |
| 5   | 실제 제목·본문·메타정보의 타입 대비가 읽기 순서와 승인 방향에 맞는가                      | 5     |
| 6   | accent의 면적·위치가 주인공 또는 합의된 브랜드 표현을 돕고 강조끼리 경쟁하지 않는가       | 1     |
| 7   | 중립색·암부·표면 대비가 해당 콘텐츠와 승인 방향에 맞는가 (틴트 자체는 통과 사유가 아니다) | 1     |
| 8   | 표면 구분이 한 가지 체계(간격 > 배경 > 그림자 > border)로 일관되는가                      | 2 · 3 |
| 9   | 밀도가 청중 · 빈도에 맞는가 (온보딩 sparse · 운영 도구 dense)                             | 9     |
| 10  | 브라우저 표면(focus ring · selection · 스크롤바 · 숫자)이 토큰을 쓰는가                   | 4 · 6 |

ko 브리프면 11번을 더한다: 한글 줄바꿈이 어절 단위이고 행간이 1.5 이상인가 (`typography-ko.md`).

`no`마다 **수정 1줄**을 적는다 — 어느 관계/구도 또는 값을 왜 바꾸는가. "더 세련되게"나
형용사를 곧바로 gradient·카드 추가로 번역하는 것은 진단이 아니다(`form-quality.md` §3).

```md
## design-loop/r1/critique.md

gates: contrast 2 fail · overflow 0 · fonts 2 · keep-all 0.6 → fix first
A. brief: 7/10 (no: 3, 6, 9)
B. craft: 6/10 (no: 3, 5, 7, 10)
critical (A1 · A8 · B1 · B2): 3/4 (no: B2)
target: B2 — 이번 라운드가 고치려는 결함
fixes:

- A3 hero CTA가 fold 아래 → hero 높이 100svh→auto, CTA를 h1 직후로
- B3 섹션 gap 전부 32px → section 96 / group 32 / item 12
- B5 h1 600 / body 400 → h1 800 -0.02em / body 400
- B7 배경과 보조 패널이 같은 명도로 합쳐짐 → 선택한 보드의 지지 면 대비로 조정, 읽기 크기에서 비교
- B10 focus ring 브라우저 기본 → --ring 토큰 2px offset 2px
```

### 전체 조화 — 섹션 비평 뒤 별도로 본다

[form-quality.md](form-quality.md)로 구성과 조형을 분리해 검토한다. 새 UI·재디자인은 전체 확장
전 대표 구간에서도 적용한다. 실제 읽기 크기에서 타입·줄바꿈·라벨/아이콘 비례를, 전체 축소에서
실루엣·색면·강약을 비교한다. 토큰·접근성 수치가 맞아도 컴포넌트가 서로 다른 조형 언어로 보이거나
핵심 콘텐츠가 장식과 경쟁하면 실패다. `어느 요소의 어떤 관계가 어긋나는가 → 선택한 방향의 근거
→ 구도 재선택 또는 국소 교정`을 기록한다. 별도의 주관적 미감 점수나 자동 합격 수치를 만들지 않는다.

전체를 축소해 큰 구도와 강약을 보고 각 섹션을 확대해 글자 · 정렬 · 여백을 확인한다.
선택한 무드보드/보존 소스와 최종 화면을 나란히 비교하고 다음을 critique에 짧게 남긴다.

레퍼런스를 응용했다면 [reference-study.md](reference-study.md)의 원본 구간 식별자와 대응 결과를
함께 연다. 원본 관계를 잘못 읽었는지, 콘텐츠 치환 조건이 안 맞는지, 선택한 관계를 구현하지 못했는지
구분해 해당 지점으로 돌아간다. 일반 craft 통과와 별개로, 중요한 관계가 결과에 남아 있는 근거를 적는다.
정확한 Fidelity 재현은 기존 fidelity.md 비교를 사용하며 응용 실험을 별도 강제하지 않는다.

- 실제 콘텐츠에서 선택한 방향의 위계 · 이미지 비중 · 밀도가 유지되는가?
- 각 섹션이 역할에 맞고 서로 다른 출처여도 하나의 타입 · 토큰 · 이미지 체계로 읽히는가?
- 연결과 배경 전환이 자연스럽고 모든 섹션이 동시에 가장 강하게 강조되지 않는가?
- 모바일에서 주요 내용 · 동작 · 긴 한국어 문구가 유지되는가?

각 결함은 기존 comparison의 대응 이미지·보존 관계·남은 차이에 연결해 §3으로 판단한다. 방향 불일치는 A6, 섹션 구성
부적합은 A7 등으로 구체화한다. 목적/콘텐츠 → 섹션 선택 → 전체 위계 → 타이포/여백 → 장식 순으로
고친다. 무드보드를 봤다는 사실로 최종 화면 검토를 대신하지 않는다.

## 3. 수정 → 재렌더 → 비교 → 모든 조건을 만족할 때만 채택

### 구성 실패 징후 — 맥락으로 판단한다

| 징후                                   | 확인 및 복구                                        |
| -------------------------------------- | --------------------------------------------------- |
| 콘텐츠 대비 큰 빈 패널                 | 여백의 역할이 없으면 실제 분량에 맞는 구도로 재선택 |
| 다른 역할의 섹션이 같은 중앙 정렬 구조 | 정보 관계가 다른데 템플릿을 반복했는지 확인         |
| 스크롤 효과 때문에 큰 카드             | 정지 상태에서 높이·읽기 경로가 적합한지 먼저 수정   |
| 핵심 이미지 대신 임의 도식             | 자산 확보 또는 자산 없이 성립하는 구성으로 전환     |
| 실제 제목·요약·메타정보에서 위계 붕괴  | 실콘텐츠로 목록·강약·모바일 재배치를 재검토         |
| 정적 문제를 모션 추가로 해결           | 탐색·선택에 도움이 되는지 확인하고 구성부터 복구    |

넓은 여백·중앙 정렬·이미지 부재를 일괄 금지하지 않는다. 승인된 방향과 콘텐츠에 적합하면 유지한다.
공통 craft 수치를 맞췄다는 이유로 이 검토를 생략하지 않는다. 구조 결함은 후보 선택으로 돌아가며
동일 범위의 복구는 자율 수행한다. 브랜드·필수 자산 처리·범위 변경이 필요할 때만 해당 결정을 묻는다.

### 수정안 비교

1. 원인이 확인된 fixes를 영향 구간에 반영한다. 국소 불만을 같은 효과의 전역 적용으로 확대하지 않는다.
2. `--out design-loop/r2`로 재렌더한다.
3. r1과 r2를 **나란히** 놓고 같은 체크리스트로 다시 답한다.
4. **채택 규칙** — 세 조건을 순서대로 본다. 통과 개수는 그중 하나일 뿐이다.

| #   | 조건                                                                                           | 위반하면                             |
| --- | ---------------------------------------------------------------------------------------------- | ------------------------------------ |
| 1   | **하드 게이트**: `gates.json`의 모든 항목이 통과한다. 미측정도 실패다                          | 무조건 반려                          |
| 2   | **치명적 무퇴행**: task 문항(A1 · A8)과 시각 핵심 문항(B1 · B2)이 yes에서 no로 되지 않는다     | 무조건 반려                          |
| 3   | **진전**: 겨눈 결함의 개선과 손실을 원본/승인 보드·수정 전후 렌더의 비교 근거로 설명할 수 있다 | 근거 부족은 미검토, 개선 없으면 반려 |

같은 기술 결과·같은 A/B 집계여도 주인공 비중·타입·밀도·시간적 전개가 나아질 수 있다.
그 차이와 허용한 손실을 비교 기록에 남긴다. 집계 증가는 시각 개선의 충분조건이 아니다.
조건 2에는 브리프의 핵심 시그니처·구성 관계도 포함한다. 총점에 숨은 치명적 회귀는 개선이 아니다.

기존 critique에 채택·반려 이유를 적는다: `r2 accept: technical unchanged; comparison <경로/구간>;
주 비주얼의 비중 복구, 긴 제목 읽기 유지; 남은 차이 <무엇·허용 이유>`.
"느낌이 낫다"·"SVG 구현 완료"·"7축 통과"만으로 승인하지 않는다. 핵심 관계 미달은 `incomplete`,
미열람·비교 근거 부족은 `unreviewed`이며 전체 확장을 멈춘다. 부분 개선의 채택이 납품 가능을 뜻하지 않는다.

## 4. 정지 규칙 — 한 요청 안에서 끝난다

**수정 채택은 상대적 개선이고 납품 가능은 핵심 결함 해소다.** 기술 게이트가 통과하거나
체크 수가 증가해도 콘텐츠 적합성·주요 정보 위계·필수 자산 조건·핵심 조형이 실패하면 디자인은 미완성이다.
구조 재선택도 합의된 작업 예산 안에서 수행하며 예산 소진 시 미해결 구조와 다음 복구 경로를
보고한다. 새 예산을 임의로 만들거나 색·간격 보정만으로 방향 실패를 완료 처리하지 않는다.

- **첫 렌더 1회 + 보수 최대 2회**(= r1 · r2 · r3). 사용자에게 돌아가기 전에 끝난다.
  라운드 2–5에서 포화한다(UI2Code^N · Sketch2Code).
- 2라운드 연속 채택되지 않으면 정지한다.
- 게이트가 마지막 라운드 뒤에도 실패하면 **게이트를 완화하지 않고** Rationale의 "남은 결함"에
  적고 완료 조건 미충족을 알린다. 방향 합의 뒤 세부 선택은 직접 끝내되, 새로 발견한 필수 사실 ·
  권한 결정은 질문한다([`one-shot.md`](one-shot.md)). 예산 소진을 완료로 보고하지 않는다.

## 4-1. 실제 앱 vs 정적 하네스 — 무엇을 검증했는지 구분한다

| 렌더 대상                  | 적는 말                 | 무엇을 보장하나                                      |
| -------------------------- | ----------------------- | ---------------------------------------------------- |
| dev server · 실제 라우트   | `validated: actual-app` | 실제 데이터 · 실제 CSS · 실제 폰트 로딩으로 측정했다 |
| `design-loop/harness.html` | `validated: surrogate`  | 토큰과 마크업만 측정했다. 통합 결함은 모른다         |

surrogate로 돌았으면 Rationale에 그대로 적는다. 하네스가 통과했다고 앱이 통과한 것은 아니다 —
반대 순서로 말하면 그것이 과장이다.

## 5. 기록

최종 보고에서 다음 판정을 분리한다. 하나의 성공으로 다른 판정을 채우지 않는다.

- technical: pass / fail / unmeasured / N/A — 실제 검사와 대상 범위
- design-self-review: ready / incomplete / unreviewed — 구성/조형 각각의 실콘텐츠·원본/견본 비교와 남은 핵심 결함
- user-acceptance: accepted / rejected / not-obtained — 실제 사용자 응답만 기록

위 상태는 설명용 기록이며 기존 코드 게이트나 외부 검증을 대체하지 않는다. 사용자 평가가 없으면
디자인 자기검토가 ready여도 사용자 만족도·실제 탐색 성과를 검증했다고 하지 않는다.

- 코드면 `design-loop/r<n>/{375,1280}-{light,dark}.png` · `metrics.json` · `critique.md`에 실제 결과를 남긴다.
  Rationale에는 `loop: r<n> · technical: <실측 결과/범위> · validated: actual-app 또는 surrogate`를 연결한다.
- 디자인/프로토타입은 프레임·viewport·상태·comparison을 연결하고 코드 검사 수치를 채우지 않는다.
  양쪽 모두 `review.md`의 기술/디자인/사용자 판정을 분리한다. 절대점수나 합계는 시각적 승인 근거가 아니다.
- 마지막 라운드 뒤에도 `no`인 항목은 Rationale의 "남은 결함 · 미확인 범위"에 옮긴다.

## 6. Impeccable이 설치된 경우 (가산)

- 1단계의 `--impeccable`은 browser 엔진 결과만 게이트에 넣는다.
- `impeccable critique <target>`은 2단계의 **두 번째 의견**이다. 우리 체크리스트가 1순위이고,
  critique의 지적은 `fixes`에 증거로 인용한다. 채택 여부는 3단계 규칙으로 판정한다.
- `impeccable polish <target>`은 루프가 끝난 뒤 finisher로 **1회**. polish 뒤에도 3단계의 세 조건으로
  한 번 더 비교하고, 조건을 하나라도 어기면 되돌린다.

### 보정 예산의 경계

선택적 finisher/polish와 그 뒤 재렌더도 기존 최대 두 번의 보수 예산에 포함한다. 예산을 모두 썼으면 추가 polish를 자동 실행하지 않는다. 핵심 경험 해석 실패는 이 미세 보정 루프가 아니라 [experience-design.md](experience-design.md) §4의 실패 기록·영향 결정 재검토로 처리한다.
