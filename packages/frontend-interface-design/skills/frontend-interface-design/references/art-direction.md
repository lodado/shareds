# Art direction — 실제 콘텐츠로 방향을 맞추고, 한 방향으로 구현한다

Discovery가 `BRIEF_READY`이면 [brand-intake.md](brand-intake.md)의 원본·토큰·누락 처리와
레퍼런스 해석을 바탕으로 방향을 정한다. 무드보드는 전체 분위기 합의 자료이고 구성 레퍼런스
보드는 섹션별 정보 관계를 찾는 자료다. 둘을 구분한다. 방향이 명확하면 제공 자료의 주석·크롭·
작은 시각 견본으로 확인하고 중복 보드/대안을 강제하지 않는다. 기존 승인 방향은 유지한다.
해석이 갈릴 때만 대안을 만든다. 최종 선택 위임은 제안 허용과 구분하며 기존 필수 승인은 유지한다.

## 레퍼런스 카드 — 링크보다 역할과 해석

처음에는 전체 방향 자료 1–2개와 필요한 보조 사례로 시작한다. 모든 섹션 자료를 사용자에게
찾아오게 하지 않는다. 정확한 URL·프레임/선택 링크·이미지와 확인한 상태를 기록한다.

| 항목             | 내용                                                  |
| ---------------- | ----------------------------------------------------- |
| 식별자/실제 출처 | URL·Figma frame·첨부·버전                             |
| 역할             | 브랜드 기준 / 시각 방향 / 구성 / 동작 / 피할 표현     |
| 적용 범위        | 전체 또는 특정 영역                                   |
| 실제 확인        | 전체 맥락·확대 이미지·상태; 동작이면 영상/상태별 자료 |
| 해석             | 가져올 특징과 이유 / 가져오지 않을 특징               |
| 충돌·적합성      | 승인 브랜드와의 충돌 / 실제 문구·이미지로 성립하는지  |

브랜드 원본은 외부 디자인 취향과 구분한다. 역할 해석이 불명확한 부분만 질문한다.
피할 표현은 제공되지 않았으면 억지로 수집하지 않는다. 상충하는 분위기를 평균 내어 섞지 않는다.

## 1. 방향 후보

방향을 새로 정하거나 해석이 갈릴 때 핵심 화면의 위계와 실제 콘텐츠로 의미가 다른 2–3개 방향을 만든다. 후보 수는
운영 휴리스틱이지 최적값이 아니다. 색만 바꾼 변형은 후보가 아니다. 각 후보는 다음 차이 중
적어도 하나를 가져야 한다: 주인공과 시선 흐름, 텍스트/이미지 비중, 정보 밀도, 대칭/비대칭,
섹션 연결 방식, 주요 인터랙션의 노출 위치. 하나를 추천하되 사용자가 방향을 고를 수 있게 한다.
후보가 사조에 기대면 `design-movement-converted.md`(경로는 `dictionary-recipes.md` §0)의 해당 사조에서 Visual Cues 중
채택 · 기각을 이름으로 적고, 반동 대상과 Lenses의 Cost를 후보 비용으로 옮긴다. 사조 이름만으로 방향을 설명하지 않는다.

각 후보에 반드시 포함한다. 보드는 실제로 materialize한 HTML/design frame/image 또는 동등한
artifact여야 하며, 생성 후 직접 열어 확인한다.

기본 산출물 예시는 `design-loop/moodboard/<direction>/index.html`과 데스크톱/모바일 캡처다.
기존 디자인 도구를 쓰면 접근 가능한 frame/link와 렌더 미리보기를 기록해도 된다. HTML은 프로젝트의
브라우저 도구 또는 `scripts/render.mjs --in <board.html> --out <direction>/render`로 렌더한다.
`board-viewed: yes`는 산출물 존재를 확인하고 **그 렌더 이미지/미리보기를 실제로 열어 본 뒤에만**
기록한다. 보드 경로, 캡처/미리보기 위치, 사용한 열람 도구와 확인 범위를 함께 남긴다. 파일을
생성했거나 캡처 명령이 성공한 것만으로 시각 확인을 완료한 것은 아니다.

- 한 문장 art direction과 primary task
- 실제 확인한 레퍼런스의 URL/출처와 확인 범위(렌더 화면, 스크린샷, 코드만 등)
- 실제 카피·실제 길이 데이터·보유 자산이 들어간 대표 UI slice
- 합의된 작은 화면의 재배치/첫 화면 조각(웹 검토 기본값 예: 375px 또는 390px)
- `관찰한 특징 → 유지할 규칙 → 가져오지 않을 부분`
- 토큰 역할: type hierarchy, color roles, spacing rhythm, surface, icon/image treatment
- 자산·권한·미확인 항목
- board artifact path와 실제로 본 responsive evidence(예: `moodboard/...`, 375/1280 캡처)

코드 설명이나 검색 결과만으로 화면을 보았다고 쓰지 않는다. 보드 artifact나 레퍼런스 미리보기를
실제로 열지 못했으면
`visual-reviewed: no (code-only)`로 표시하고, 적용 완료로 보고하지 않는다. 실제로 보유하지 않은
이미지·후기·수치·로고·카피를 만들어 넣지 않는다. 명시적으로 허용한 예시 시안은 예시임을 표시하고
실제 자산이 적용된 결과로 보고하지 않는다.

## 2. 선택과 경계

무드보드는 분위기를 맞추고 **실제 콘텐츠 대표 구간**은 구성의 성립을 확인한다. 새 구성의 핵심
불확실성이 남으면 위 대표 UI slice를 제목·요약·메타정보·보유 자산이 들어간 고충실도 견본으로
구체화한다. 항상 hero일 필요는 없다. 글 발견이 목적이면 대표 글과 목록을 함께 확인한다.
기존 승인 소스가 이를 이미 보여주면 별도 견본·승인 단계를 반복하지 않는다.
주제나 데모 데이터 사용에 대한 동의를 아직 보여주지 않은 시각 방향의 승인으로 확대하지 않는다.

사용자가 선택하면 선택된 방향을 `decision record`에 고정하고, 이후 섹션 구조·토큰·컴포넌트는
skill이 조합한다. 사용자가 방향 선택까지 위임했거나 이미 방향이 결정된 경우에는 근거를 적고
직접 선택한다. 기존 Fidelity 요청, 잠긴 `DESIGN.md`, 사용자 소유 소스, 필수 approval 범위는
이 절차보다 우선한다. 명시적 redesign이 승인된 범위에서만 기존 스타일을 바꾼다.

moodboard는 다음을 결정하지만 모든 섹션을 같은 레이아웃으로 강제하지 않는다.

- 공유: 글자 위계, 색상 역할, 정렬 기준, 여백 단계, 표면/테두리/모서리 계열, 아이콘 계열
- 자유: 섹션 레이아웃, 이미지 비중, 정보 묶음, 강조 위치, 배경 전환, 높이, 인터랙션 표현

## 3. 기록 형식

```md
## Art direction

- chosen: <direction id> · selected by user | delegated | locked fidelity
- observed: <실제로 본 특징과 출처>
- keep: <콘텐츠 관계와 시선 흐름>
- adapt: <우리 토큰·카피·반응형에 맞출 것>
- avoid: <복제하지 않을 브랜드 장식·자산·구조>
- visual-reviewed: yes | no (code-only) · scope=<범위>
- board: <artifact path> · board-viewed: yes | no · responsive evidence: <path/범위>
- asset gaps: <none 또는 구체적 항목>
```

## 4. 이미지 제작 브리프 — 자산이 없고 제작이 승인된 경우에만

제공된 자산으로 성립하는 화면에는 쓰지 않는다. 필수 이미지가 없고 사용자가 제작(생성 · 촬영 · 일러스트)을 승인했을 때만
`visual-asset-taxonomy.md` → 기법(Part 1) · 구조(Part 2) · 표면(Part 3) 이름으로 브리프를 쓰고, `Build` 열(SVG / Image(gen) /
Hybrid)로 제작 수단을 정한다. 사진풍이면 `generative-image-taxonomy.md`의 Spec · Prompt Fragment, 상업 사진 수준이면
`commercial-photographic-taxonomy.md`의 장르 → 스펙 순서와 Part 10 물리 정합성(피부 · 그림자 · 반사 · 원근)을 검수 항목으로
옮긴다(경로 · 읽는 법은 `dictionary-recipes.md` §0. 로컬 스냅샷이 없으면 3축 이름만으로 쓰고 그 사실을 적는다).
설치된 이미지 생성 스킬이 있으면 브리프를 넘기고, 결과 이미지는 직접 열어 물리 정합성을 확인한 뒤에도 사용자 승인 전까지
"확인 필요"다. 브랜드 로고 · 실제 인물 · 제3자 제품을 생성해 채우지 않는다.

## 근거

- [Lucero, 2012 — Framing, Aligning, Paradoxing, Abstracting, and Directing: How Design Mood Boards Work](https://doi.org/10.1145/2317956.2318021): 초기 디자인에서 moodboard가 framing·aligning·directing을 돕는다는 관찰이다.
- [Dow et al., 2010 — Parallel Prototyping](https://doi.org/10.1145/1879831.1879836): 초보자의 웹 광고 제작 실험에서 병렬 대안이 탐색과 평가에 유리했던 범위의 연구다. 2–3개는 운영 예산이며 품질 보장을 뜻하지 않는다.
