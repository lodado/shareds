# Section implementation — 화면을 섹션별 구현 지시로 바꾼다

화면 구현·구현 프롬프트·개발 핸드오프를 만들 때 읽는다. `section-composition.md`에서 고른 역할과
구도를 **어디에 무엇을 놓고, 무엇을 하면 어떻게 바뀌며, 어떻게 확인할지**로 풀어 쓴다.
이미 구현을 요청받았다면 이 명세는 중간 산출물이다. 섹션마다 재승인을 요구하거나 계획만 내고 끝내지 않는다.
문서·디자인 제안만 요청받았으면 합의된 형식으로 명세를 전달하고 제품 파일은 수정하지 않는다.

## 1. 화면의 읽기 순서를 먼저 나눈다

사용자 과업을 기준으로 섹션에 안정적인 ID를 붙이고 다음 지도를 만든다.
랜딩은 가치 제안 → 작동 방식 → 비교 → 행동일 수 있고, 업무 화면은 탐색 → 검색/필터 → 결과 → 상세일 수 있다.
이는 예시이며 hero·카드·CTA를 모든 화면에 끼워 넣거나 섹션 수를 고정하지 않는다.
앱의 동시 표시 영역은 위아래 스택으로 오해하지 않도록 배치 관계도 적는다.

| ID / 섹션 | 사용자 질문·역할            | 실제 콘텐츠 / 핵심 행동 | 위치·앞뒤 또는 병렬 관계               |
| --------- | --------------------------- | ----------------------- | -------------------------------------- |
| S1 / 이름 | 여기서 무엇을 이해·완료하나 | 문구·데이터·행동        | 첫 화면/아래/왼쪽 등, 다음 섹션과 연결 |

전역 컨테이너·타입 스케일·간격·색·아이콘·공유 상태는 한 번만 정의하고 섹션에서는 토큰을 참조한다.
기존 프로젝트의 값과 컴포넌트를 우선 사용한다. 새 값이 필요하면 이유와 값을 토큰 정의에 모은다.
일부 섹션 수정에는 해당 섹션과 인접 영향만 적고, 잠긴 레이아웃이나 제품 정책을 다시 설계하지 않는다.

## 2. 사전 용어를 구현 결정으로 번역한다

사전은 구도를 선택하는 어휘이지 그 자체로 구현 명세나 관측 증거가 아니다.
`용어 → 이 콘텐츠에 맞는 이유 → 구체적인 배치/동작 → 좁은 화면의 변화`까지 쓴다.
필요한 항목만 선택한다. 모든 사전·기법을 읽거나 화면에 적용할 필요는 없다.

사용자가 사전 파일/경로를 제공하면 선택한 패턴 ID 또는 제목으로 원문을 찾아 `Description`,
`Build`, `Best For`, `Avoid For`, 반응형 조건을 확인한다. 파일을 열지 않고 원문을 확인했다고 쓰지 않는다.
원문이 없는 배포 환경에서는 [dictionary-recipes.md](dictionary-recipes.md)의 발췌·해석을 사용하되
`패키지 내 요약 참조`로 표시한다. 매번 전체 사전이나 작성자의 Downloads 경로를 요구하지 않는다.
이 레시피에는 요금제 비교·롱리드·스크롤 설명 섹션의 구체적인 지시 예시가 있다.

| 참고 개념                                                   | 구현 지시에 포함할 결정                                                                                                                 |
| ----------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| Layout: 목적/아키타입 + required/optional/responsive        | 화면 역할과 필수 구조를 분리한다. 선택 장식은 필수 정보와 혼동하지 않는다.                                                              |
| `comparison-table` + `reflow-reorder`                       | 비교할 행·열·정렬 기준, 헤더, 좁을 때 재배치 또는 표 내부 스크롤, 비교 문맥 유지 방법을 정한다.                                         |
| `sidebar-nav-shell` / `dashboard-grid`                      | 탐색·본문·보조 영역의 실제 위치, Grid/Flex 구조와 폭 제한, 모바일 탐색 방식, DOM 읽기 순서를 정한다.                                    |
| `dominant-entry-point` / `visual-anchor`                    | 첫 시선에 놓일 실제 제목·수치·이미지와 보조 정보의 비중을 정한다. 강조점을 늘려 모두 경쟁하게 하지 않는다.                              |
| UX: Search → Filter → List → Detail                         | 검색 범위·실행 시점, 필터 선택/해제, 결과 갱신, 상세 진입과 돌아왔을 때 보존할 상태를 정한다.                                           |
| UX: loading / empty / error / success                       | 발생 조건, 표시 위치·문구, 재시도·복구 행동을 적는다. 정책이 확정되지 않은 낙관적 갱신·자동 저장은 임의로 추가하지 않는다.              |
| Typography: 역할·행 길이·줄바꿈·유동 크기                   | 제목/본문/라벨 토큰, 최대 읽기 폭, 긴 한글·URL 처리, 폰트 대체 시 배치 변화를 정한다. 한국어는 `typography-ko.md`를 우선한다.           |
| Visual Asset: Full Bleed / Layered·Overlap / Negative Space | 실제 자산과 크롭 초점, 비율·예약 공간, 겹침 순서·텍스트 보호, CSS/SVG 등 구현 수단을 정한다. 이미지가 없으면 가짜 커버를 만들지 않는다. |

예: “모던한 split hero” 대신 “제목·설명·CTA를 시작 열에, 제공된 제품 화면을 끝 열에 둔다.
넓은 화면은 Grid 두 열, 좁은 화면은 제목 → 설명 → CTA → 제품 화면의 DOM 순서로 한 열로 바꾼다.
스크린샷은 원본 비율을 보존하며 CTA는 기존 문의 경로로 이동한다”처럼 쓴다.
실제 폭·간격·전환점은 프로젝트 토큰이나 새 토큰 정의로 결정한다.

## 3. 섹션별 구현 명세

아래 형식을 섹션마다 적용하되 공통 결정은 참조하고 해당 없는 항목은 이유와 함께 생략한다.
단순 정적 문단에 loading 상태나 복잡한 모션을 억지로 만들지 않는다.
CSS 예시는 코드 산출물에 적용하고, 디자인 도구에서는 대응하는 frame·auto-layout·variant로 표현한다.

```md
### S<번호> — <섹션 이름>

- 참고 근거: 사전 파일 + 패턴 ID/제목, 채택한 구조와 피한 조건.
  원문 추천과 이번 화면에서 정한 수치·모바일/접근성 조정을 구분. 사전을 쓰지 않았다면 출처를 꾸미지 않음.
- 목적·완료 행동: 사용자 질문, 핵심 정보, 다음 행동/연결 섹션.
- 콘텐츠·위계: 실제 문구/데이터 출처, 제목 → 근거 → 행동 순서, 없는 필수 자료 처리.
- 배치: 선택 패턴과 이유, DOM/landmark·컴포넌트 트리, Grid/Flex/flow,
  열·행·비중·최대 폭·정렬·간격 토큰, 인접 섹션 경계. 대안을 나열하지 말고 하나를 선택.
- 시각·자산: 제목/본문/라벨 토큰, 읽기 폭·줄바꿈, 표면·강조 토큰,
  실제 자산 경로/출처·비율·크롭·alt 또는 장식 처리. 없으면 콘텐츠 중심 구성.
- 동작·상태: 대상 → trigger → state 변화 → 보이는 feedback → 완료/실패·복구.
  링크 목적지, 입력 범위/검증, 제어별 필요한 상태, 공유 상태의 소유자와 유지 범위.
- 모션: 대상·트리거·변화 속성·시간/이징 토큰·종료 상태, 중단/반복 조건,
  reduced-motion 대안. 모션이 없으면 없음과 이유. 정지 상태에서도 정보와 행동은 유지.
- 반응형·접근성: 실제 전환점 또는 콘텐츠 제약, 열/순서/탐색 변화,
  긴 콘텐츠·overflow 처리, 키보드 조작·focus 이동/복귀·이름/상태 알림.
- 구현 대상: 확인한 기존 파일/컴포넌트/프레임과 재사용 대상, 필요한 변경.
  새 대상은 제안임을 표시. 미확인 경로·API를 기존 구현인 것처럼 쓰지 않음.
- 확인: viewport·상태·입력/조작 → 관측 가능한 기대 결과. 증거 또는 미검증 표시.
```

API·저장·권한·삭제 정책은 기존 계약을 참조한다. 없는 기능을 디자인 판단으로 만들어 넣지 않는다.
기술 스택이 미정인 문서 요청에는 구조·상태 소유 관계를 먼저 명시하고 프레임워크 선택을 필수로 만들지 않는다.
전체 결정 요약은 기존 40줄 한도를 유지하고, 상세 명세는 합의된 문서/응답의 별도 절에서 연결한다.

## 4. 예시 — 자료 탐색 화면의 세 섹션

조건: 제목·요약·태그·상세 URL이 있는 정적 자료 목록, 썸네일 없음, 검색·태그 필터는 이미 승인됨.
S1 탐색 헤더 → S2 검색/필터 → S3 결과 목록으로 나눈다. 검색과 목록의 필터 상태는 부모 화면이 소유한다.
이 예시의 수치·문구·태그 조합은 설명용 선택이며 다른 제품의 기본 정책이 아니다.

- **공통:** 예시 토큰을 `content-max: 72rem`, `gutter: 1.5rem / narrow 1rem`, `section-gap: 3rem`,
  `control-gap: 0.5rem`, `bp-narrow: 48rem`으로 정의한다. 실제 작업에서는 기존 토큰으로 치환한다.
- **S1 / 탐색 헤더:** H1 “자료실”과 제공된 소개 문구를 문서 흐름으로 배치한다.
  페이지 제목은 기존 heading 토큰, 설명은 body 토큰과 읽기 폭 토큰을 쓴다. 버튼·커버는 추가하지 않는다.
  구현 대상은 기존 페이지 헤더를 우선 확인하며, 좁은 화면에서도 제목 → 설명 순서와 전체 제목을 보존한다.
- **S2 / 검색·태그:** 이름 있는 search form 안에 label·input·submit button을 둔다.
  넓으면 입력과 버튼을 한 행으로, `bp-narrow` 미만이면 세로로 배치한다. 태그 버튼은 다음 행에서 줄바꿈한다.
  Enter/검색 버튼 → 제출된 질의 갱신 → 제목·요약을 필터링한다. 태그는 예시에서 단일 선택이며
  `aria-pressed`로 표시한다. 초기화 → 질의·태그 해제 → 전체 결과와 개수를 복원한다.
- **S3 / 결과:** 필터링한 자료를 `ul > li > article`로 렌더한다. 제목 링크 → 요약 → 태그 순서의 한 열 목록으로,
  공통 기준선과 간격을 공유한다. 이미지 없는 큰 커버나 모든 행을 감싸는 장식 카드는 만들지 않는다.
  제출 결과 개수는 별도 `aria-live="polite"` 영역에서 알리고 focus는 조작한 검색/필터에 유지한다.
  0건이면 “조건에 맞는 자료가 없습니다”와 필터 초기화 버튼을 보여준다. 실제 상세 URL로 이동한다.
- **상태·모션:** 검색 버튼/태그/링크에 역할별 hover·focus-visible·active 상태를 제공한다.
  로컬 동기 필터이므로 network loading/error는 해당 없으며, 결과 전환에 지연 애니메이션을 넣지 않는다.
  reduced-motion에서도 검색·선택·결과 갱신은 동일하게 작동한다.
- **구현·확인:** 기존 페이지·검색 컨트롤·목록 컴포넌트를 먼저 찾아 S1–S3에 연결한다.
  파일 구조가 주어지지 않은 이 예시는 경로를 지어내지 않는다. 375/1280px에서 긴 한글 제목과 긴 URL,
  0/1/다수 결과, Enter 제출·태그 선택·초기화를 확인한다. 페이지 가로 넘침 없음, 입력/버튼 겹침 없음,
  키보드 focus 표시와 결과 개수 알림, 초기화 후 전체 결과 복원이 기대 결과다.

## 5. 명세에서 구현·검증으로

구현 요청이면 공유 토큰/상태 → 대표 섹션 → 나머지 섹션 순으로 진행한다.
각 섹션 ID를 실제 구현 위치와 연결하고 `form-quality.md`·`look.md`의 대표 구간 검토를 재사용한다.
화면 전체의 읽기 순서와 섹션 간 상태 연결도 확인한다. 개별 섹션이 좋아도 전체 과업이 끊기면 완료가 아니다.
문서만 만든 경우에는 구현·렌더 완료를 주장하지 않는다. 구체적인 명세도 실제 시각 검토의 대체 증거는 아니다.

전달 전에는 남겨 둔 미결정 대안과 지어낸 상태를 점검한다. 위임된 배치에 “한 열 또는 두 열”,
“skeleton 또는 spinner”를 그대로 남기지 말고 콘텐츠에 맞는 하나를 선택한다. 미확정 제품 사실과
직접 결정할 디자인 세부를 구분한다. 제공된 정적 자료를 동기 필터링하는 화면에 network loading/error나
서버 요청을 추가하지 않는다. 실제 비동기 계약이 있을 때만 해당 발생 조건과 복구를 명세한다.

## 참고 자료와 적용 범위

사용자가 제공한 Vibe Dictionary Markdown 묶음의 아래 항목을 선택·재구성했다. 사전 전체를 복제하지 않는다.
이 파일은 필요한 번역 규칙을 포함하므로 배포 후 원래 Downloads 경로나 외부 열람에 의존하지 않는다.

- `layout-taxonomy.md` — 대표 조합 구성, 구조·레이아웃, 반응형: [Layout Taxonomy](https://vibedesignlab.net/dictionary/layout-taxonomy)
- `ux-taxonomy.md` — 검색/필터, 흐름, 동작·상태: [UX Taxonomy](https://vibedesignlab.net/dictionary/ux-taxonomy)
- `typography-taxonomy.md` — 역할·행 길이·줄바꿈·반응형: [Typography Taxonomy](https://vibedesignlab.net/dictionary/typography-taxonomy)
- `visual-asset-taxonomy.md` — 구도·프레이밍·구현 매핑: [Visual Asset Taxonomy](https://vibedesignlab.net/dictionary/visual-asset-taxonomy)

링크는 제공된 자료의 출처 표기이며 이번 작업에서 라이브 사이트를 관측했다는 뜻이 아니다.
분류 체계의 추천은 사용자 소스·프로젝트 토큰·접근성·실제 콘텐츠보다 우선하지 않는다.
