# HCI → reference → wireframe — Figma 전에 무엇을 왜 만들지 보여준다

새 화면·주요 구성/행동 변경·와이어프레임 요청에 적용한다. HCI는 장식 목록이 아니라
**특정 사용자가 특정 맥락에서 과업을 이해하고 실행하며 실패에서 회복하게 만드는 설계**다.
좋은 패턴을 썼다고 사용성이 입증되는 것은 아니다. 아래 산출물은 검증할 설계 가설이다.

## 1. 과업부터 정한다

[5개 계층과 Grill 질문](request-contract.md) §3을 기존 brief에 연결한다.
Strategy·Scope의 목적/범위에서 Structure의 흐름을 도출하고 Skeleton의 배치로 옮긴다.
조사·스케치는 겹칠 수 있으며 새 모순이 있을 때만 해당 결정을 묻는다. 별도 계층별 승인 절차는 없다.

PRD와 내부 화면에서 아래를 추출한다. 이미 받은 답을 다시 묻거나 가짜 persona·사용자 조사·목표 수치를 만들지 않는다.
불명확하지만 방향을 바꾸지 않는 내용은 `제안/미확인`으로 표시한다. 제품 방향을 바꾸는 충돌만 질문한다.

| HCI 브리프    | 기록할 내용                                                      |
| ------------- | ---------------------------------------------------------------- |
| 사용자와 맥락 | 누구인가, 숙련도·빈도·사용 기기·환경 제약은 무엇인가             |
| 핵심 과업     | 사용자가 무엇을 끝내려 하는가; 기능명보다 사용자 언어로 한 문장  |
| 진입과 정보   | 어디서 시작하고 무엇을 알아야 판단할 수 있는가                   |
| 성공 신호     | 사용자가 완료를 어떻게 아는가; 실제로 관측할 완료·오류·복구 기준 |
| 위험과 경계   | 잘못된 선택의 비용, 데이터 확정 시점, 취소·되돌리기 가능 여부    |

제품 UI는 `진입 → 정보 인식 → 선택/입력 → 실행 → 피드백 → 다음 행동`으로,
랜딩은 `방문 목적 → 가치 이해 → 실제 근거 → 판단 → CTA/다음 경로`로 연결한다.
랜딩에도 필요한 CTA 결과·탐색 동작은 설명하되, 상태표를 채우려고 폼·로딩·모달을 추가하지 않는다.
상세 persona, 전체 journey map, 대규모 상태 머신은 현재 결정에 필요할 때만 만든다.

핵심 행동별로 다음 표를 짧게 쓴다. 존재하는 상태와 제안한 상태를 구분한다.

| 시작 상태     | 사용자 행동/트리거 | 시스템 결과·보이는 피드백    | 실패·취소·복구                    | 키보드·포커스                        |
| ------------- | ------------------ | ---------------------------- | --------------------------------- | ------------------------------------ |
| 예: 입력 완료 | 저장 실행          | 진행 중임을 표시 → 성공 확인 | 입력 유지 + 오류 원인 + 다시 시도 | 실행 요소와 결과를 찾을 수 있는 순서 |

관련 있는 empty/loading/success/error/permission 상태만 포함한다. 입력 검증 시점, 데이터 확정 시점,
재시도의 중복 실행 위험, 뒤로 가기 시 입력 보존은 과업에 필요한 경우 명시한다.
백엔드 보장이나 실제 assistive technology 동작을 설계 표만으로 구현·검증했다고 하지 않는다.

## 2. 여러 레퍼런스를 같은 질문으로 비교한다

[taxonomy 계약](taxonomy-reference-workflow.md)과 [research selection](research-selection.md)을 재사용한다.
내부 적합성을 먼저 확인한다. 다중 비교가 요청되었거나 새 흐름의 근거가 부족하면 **서로 다른 출처**를 비교한다.
보통 과업이 유사한 사례 2–3개와 필요한 공식 패턴 지침이면 시작할 수 있다. 숫자는 품질 점수나 무한 검색 의무가 아니다.
부족한 출처는 부족하다고 남긴다. 외부 컴포넌트 비교의 필수 수량·권리·반입 검증은
[component source gate](component-source-gate.md)를 별도로 따르며, 아래 문서 비교로 대신하지 않는다.

검색은 `사용자 과업 + UI 역할 + 필요한 상태/기기`로 좁힌다.
예: `invite members review errors`, `search results empty state mobile`.
이는 검색 의도 예시이며 사전 ID나 실제 조회 결과가 아니다. 실제 제품/화면은 현재 과업에 맞게 고른다.
NN/g 같은 원칙 자료는 판단 근거, GOV.UK 같은 패턴 자료는 행동 지침, 제품 화면은 관측 사례다.
어느 것도 편집 가능한 Figma 자산을 자동으로 제공하지 않는다.

기존 Reference Log에 비교 행을 보탠다. 별도 DB나 새 JSON schema는 만들지 않는다.

| 출처·관측 수준                             | 과업 적합성                       | 역할               | 채택 / 기각 / 변형            | 적용 위치·검증할 가정                    |
| ------------------------------------------ | --------------------------------- | ------------------ | ----------------------------- | ---------------------------------------- |
| 실제 URL/frame + 조회일 + 확인한 상태/기기 | 숙련도·빈도·콘텐츠 밀도·오류 비용 | 구조 / 행동 / 시각 | 무엇을 왜 가져오거나 버리는가 | 와이어프레임 번호 → 이후 실제 Figma node |

- **구조:** 정보 우선순위, 그룹, 읽기 순서, 화면 간 관계를 가져온다.
- **행동:** 트리거, 상태 전이, 검증, 피드백, 취소/복구를 참고한다.
- **시각:** 승인된 내부 시스템·선택 템플릿 하나가 서체·색·간격·컴포넌트 언어를 소유한다.
  외부 구조를 가져온다고 그 사이트의 색·폰트까지 섞지 않는다.

한 출처가 여러 역할을 제공할 수 있지만 각 근거는 따로 확인한다. 이 역할 구분은 기존 PRD→brand→내부 자산의
권한 순서를 바꾸지 않는다. 외부 패턴은 제품 정책이나 접근성 요구를 덮어쓰지 못한다.
자동 저장 편집기와 검토 후 제출 폼처럼 데이터 확정 모델이 충돌하면, PRD·오류 비용에 맞는 모델을 선택하고
다른 모델을 버린 이유를 쓴다. 둘의 버튼·전환을 임의로 섞지 않는다.

**관찰과 추론을 분리한다:**

- 정적 화면에서 확인한 그룹·문구·위계는 `관찰`로 기록한다.
- 공식 문서가 설명하는 동작은 `문서 근거`다. 대상 서비스에서 직접 실행한 관측과 구별한다.
- 스크린샷에 없는 저장 시점, debounce, 로딩, 오류, Tab 순서, 포커스 복귀, 스크린리더 알림,
  모바일 재배치·모션은 `제안/미검증`이다. 정적 화면을 보았다는 이유로 동작을 확인했다고 하지 않는다.
- 실제 제품 흐름·접근 가능한 prototype·공식 문서로 필요한 근거를 보완한다.
  확보하지 못한 자산·동작은 HOLD/미확인으로 남기고 독립적인 준비만 계속한다.

## 3. 대상 Figma 쓰기 전에 러프 스케치와 설명을 보여준다

읽기 전용 Figma 조사·레퍼런스 관측은 먼저 해도 된다. **첫 대상 canvas 변경 전에** 아래 묶음을
대화에 출력한다. 내부 파일에만 저장하는 것은 “먼저 보여주기”가 아니다.
후보 import/복제·비교 영역 생성도 쓰기이므로 이 설명 뒤에 한다. 읽기 전용으로 확인한 후보의 매핑은
잠정안이며, 아직 수행하지 않은 반입·실콘텐츠 비교를 완료했다고 쓰지 않는다. 사전 설명 뒤 출처 게이트를
통과해 후보를 확정하고, 비교 결과로 동선이나 구성이 바뀌면 그 이유를 다시 설명한다.

1. 과업과 추천 구조 한 문장.
2. 레퍼런스 비교의 채택·기각 이유와 확인하지 못한 사항.
3. 번호가 붙은 ASCII/text 와이어프레임: 실제 의미의 제목·정보·주요 CTA·이동 관계.
4. 주요 성공 경로와 가장 중요한 실패/복구 상태, 관련 키보드·포커스 의도.
5. “왜 이 순서인지 / 누르면 무엇이 일어나는지 / Figma에서 어떤 검증된 자산으로 옮길지”.

기본은 핵심 화면/상태 1–3개다. 전체 범위가 더 크면 먼저 흐름을 요약하고 결정에 중요한 부분만 펼친다.
범위에 있는 기기를 기준으로 한다. desktop/mobile 둘 다 요청되었다면 모바일 읽기 순서·CTA 재배치 차이를
작게 덧붙인다. desktop만 요청한 작업에 모바일 시안을 강제하지 않는다.
색·그라데이션·정교한 폰트·이미지 생성·HTML 구현은 이 설명에 필요 없다.
스케치의 박스는 역할 표시이며, 실제 Figma에서 확보한 원본을 무시하고 rectangle로 재그릴 허가가 아니다.

### 설명 예시 — 팀 초대, 제품 사실이 아닌 가상 설계 제안

가정: 관리자가 멤버를 초대하며 전송 전 수신자 확인이 필요하다는 PRD가 있다. desktop 범위만 예시로 든다.
실제 프로젝트에서는 PRD와 관측한 레퍼런스로 바꾼다. 아래 역할 이름은 실제 Figma component ID가 아니다.

```text
[1. 초대 대상 입력]                    [2. 전송 전 확인]
+--------------------------------+    +--------------------------------+
| 팀에 멤버 초대                  |    | 초대 내용 확인                 |
| 초대받을 이메일                |    | 받는 사람: [입력한 이메일]     |
| [이메일 입력________________]  |    | 권한: [앞에서 선택한 권한]     |
| 권한 [멤버 v]                  |    | [수정]                         |
| 이 권한으로 할 수 있는 일 설명 |    | 전송하면 초대 메일이 발송됩니다|
|                                |    |                                |
| [취소]           [초대 검토 →] |--->| [뒤로]          [초대 보내기]  |
+--------------------------------+    +--------------------------------+
                                                   |
                         전송 중 → 성공 확인 또는 오류/재시도
```

| 번호/상태 | 동작과 설계 이유                                                            | Figma 매핑·확인할 것                                           |
| --------- | --------------------------------------------------------------------------- | -------------------------------------------------------------- |
| 1 입력    | 이메일→권한→검토 순서. 라벨·권한 설명으로 기억 부담을 낮춘다                | 내부 form/input/select/button 후보 확인, 긴 이메일 줄바꿈      |
| 1 오류    | 잘못된 입력을 텍스트로 식별하고 값은 유지한다                               | error variant 및 오류 위치/포커스 의도; 색상만으로 알리지 않음 |
| 2 검토    | 발송 전에 대상·권한을 다시 인식하고 수정한다                                | summary 패턴의 적합성, 뒤로 갔다 돌아왔을 때 값 보존           |
| 전송 중   | 클릭 결과를 즉시 보이고 중복 실행을 방지할 동작을 제안한다                  | loading 상태; 서버 중복 방지는 별도 구현 요구로 남김           |
| 성공/실패 | 성공은 무엇이 완료됐는지, 실패는 무엇을 유지하고 어떻게 재시도할지 설명한다 | success/error 상태 및 prototype 경로; 미지원 검증은 미검증     |

설명: “먼저 대상을 입력하고 권한의 의미를 확인합니다. 검토 화면은 잘못된 발송의 비용 때문에 둡니다.
전송 후 성공과 실패를 구분하고, 실패해도 입력을 다시 하지 않게 합니다. GOV.UK의 check-answers에서는
검토·수정 관계만 참고하고, 시각 언어는 내부 시스템을 유지합니다. 단순 저위험 자동 저장이라면 이 검토 화면은 빼겠습니다.”

이 예시는 특정 서비스의 동작을 관측한 결과가 아니며, Figma 자산 확보나 사용성 테스트 통과를 뜻하지 않는다.
완료율·오류율 개선도 실제 사용자 관측 전에는 가설이다.

## 4. 설명 이후의 진행·정지와 기록

- “먼저 설명해줘”만 있고 세부 작업을 위임받았다면 보여준 뒤 기존 권한·출처 게이트 안에서 계속한다.
  설명을 `accepted`로 기록하거나 “진행할까요?”를 반복하지 않는다.
- “내 확인을 기다려 / 승인 전 수정하지 마”가 있으면 첫 대상 쓰기 전에 멈춘다.
  사용자 확인은 `not-obtained`로 남기고 실제 답을 받은 뒤 해당 범위만 진행한다.
- 쓰기 권한이 없어도 읽을 수 있는 자료로 HCI·비교표·텍스트 스케치를 준비할 수 있다.
  최종 Figma 제작은 BLOCKED이며, 스케치 완료를 PILOT_READY/FIGMA_READY로 보고하지 않는다.
- 작은 오타·간격 변경처럼 구조·행동을 보존하는 작업은 기존 과업/근거를 연결하고 생략 이유 한 줄만 남긴다.
  사용자가 스케치를 명시 요청했다면 작은 작업이어도 필요한 부분을 보여준다.

새 workflow 상태나 승인 필드를 만들지 않는다. HCI 브리프는 기존 요청의 `brief`·`scope.states`와 연결하고,
비교표·스케치·설명 위치는 Reference Log에 둔다. handoff의 `source_trace.references`에서 로그를 연결하고
`handoff.summary`/`handoff.next_action`에 준비 결과·남은 결정/권한을 요약한다.
준비 도중 미확보인 실제 Figma ID는 만들지 않는다. 기존 schema에 임의 최상위 필드를 추가하지 않는다.

## 5. Figma 전환과 검증

시각 방향이 미정이거나 대안이 요청되었다면 [시각 방향 비교](visual-direction.md)를 적용한다.
텍스트 스케치 다음에 실제 원본 기반의 작은 시각 대안을 비교·선정하며, 전체 화면을 먼저 만들지 않는다.
고정된 방향은 재사용하고, 후보 반입·대안 제작도 사전 설명 및 명시된 검토 대기 이후에 한다.

[Figma composition](figma-composition.md)에 따라 `와이어프레임 번호 → 채택 근거 → 확보한 원본/component →
적용 frame/state`로 매핑한다. 원본·연결·edit mode를 보존하며 실제 콘텐츠로 pilot을 만든다.
러프 스케치를 더 좋은 근거로 바꾸는 것은 가능하지만, 바뀐 동선/상태와 이유를 로그에 남긴다.
제품 정책이나 승인된 범위를 바꾸는 변경은 해당 결정을 다시 확인한다.

스케치 단계에서는 아래 질문으로 **자체 과업 walkthrough**를 한다.

- 사용자가 어디서 무엇을 해야 할지, 행동 결과와 완료를 알 수 있는가?
- 가장 중요한 오류에서 정보 손실 없이 복구하거나 취소할 수 있는가?
- 키보드 사용의 읽기/포커스 순서와 결과 인식이 설계되어 있는가?

Figma에서는 합의된 화면·상태와 실제 prototype 경로를 다시 확인한다. 정적 frame은 동작 검증이 아니다.
prototype이 표현하지 못하는 네트워크·실제 키보드/스크린리더 동작은 미검증으로 남기고,
합의된 필수 검증이 남아 있으면 [delivery contract](delivery-contract.md)의 완료 게이트를 통과시키지 않는다.
Figma prototype, 자체 walkthrough, 실제 사용자 과업 테스트, 제품 코드 QA는 서로 다른 증거다.
통과 선언 대신 관측한 범위·문제·수정·남은 검증을 구분한다.
